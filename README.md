# 暖陽動物之家｜認養配對所

以「嚴謹認養手續」為喻的交友配對網站原型。男生登記為 🐶 狗狗、女生登記為 🐱 貓咪；
想認識誰就提出認養申請，通過三階段審查（書面審查 → 價值觀評估 → 日常觀察）才會互相
解鎖聯絡方式。

- `index.html` — 公開配對站：訪客可先看首頁、流程說明與隱私權，登入／註冊位於右上角；登入後可使用
  佈告欄（含檢舉）、**個人中心**（我的資料、我的收件匣、
  我的申請、第二階段雙向對話、我的回覆範本、診療點數）、**管理後台**（只有 `is_admin`
  帳號看得到：全站統計、會員停權／刪除、檢舉處理、範本主檔管理、照片與驗證照審核台）、
  隱私權政策、流程說明。
  「我的資料」的自介欄位除了自由文字，還有一組結構化的選填欄位（年收入區間、婚姻狀態、
  是否有孩子、兵役狀況、居住狀況、負債狀況、關係期待、生育規劃、MBTI、興趣／個性／
  生活習慣多選），以及「希望對方的條件」（婚姻要求、年齡範圍、孩子要求、生活習慣要求）；
  佈告欄卡片上會摺疊成一個「詳細資料」區塊顯示給別人看。
- `dashboard.html` — 個人後台，依登記身分顯示不同內容：
  - **待認養**（被追求的一方）：收件審查（通過／婉拒／解鎖）、自訂第一階段題目、
    第二階段價值觀題庫（十類 48 題可勾選）、罐頭回覆庫、AI 建議評分（免費、不扣點）。
  - **飼主**（提出申請的一方）：送出的申請進度、私人筆記、回答小抄。
- `shelter-review-assistant.html` — **私人工具**，只綁定站長本人的會員帳號
  （`js/config.js` 的 `OWNER_EMAIL`），跟平台的多人資料模型完全分開
  （不使用 `profiles`／`applications`），資料存在 `owner_kv` 資料表（每個帳號各自隔離，見第 6 步）。用來管理小橘的 Dcard 企劃：病例設定、罐頭回覆、FAQ、貼文申請書、
  表單匯入評分、AI 判斷該用哪封罐頭。登入後會在「個人中心 → 我的資料」看到這個工具的連結
  （只有站長本人的帳號登入時才會顯示）。
- `supabase-schema.sql` — 資料庫結構與 RLS（Row Level Security）政策，包含
  `match_profiles`／`applications`／`match_messages`（配對平台）、`reports`（檢舉）、`template_master`（範本主檔）、
  `owner_kv`（私人工具專用，只有本人存取得到）。
- `js/config.js` — 你的 Supabase 連線設定（網址＋anon 金鑰＋選用的 AI 代理網址）。
- `js/supabase-client.js` — 共用的登入／資料存取邏輯（配對平台與私人工具共用同一份）。
- `supabase/functions/claude/index.ts` — （選用）Claude API 代理，讓照片初檢、主治獸醫評估、
  「AI 建議評分」、私人工具的審查草稿產生都能安全呼叫 AI，金鑰只存在伺服器端，
  瀏覽器端一律不會直接呼叫 `api.anthropic.com`。

## 這份 README 適用哪一種情況

**維護目前這個正式站**：`js/config.js` 已經指向正式的 Supabase 專案（Project URL、
anon key、Claude 函式網址都填好了），**不需要重填**。下面的「建立 Supabase 專案」
是給第二種情況看的。你要做的通常只有改程式、推上 `main`，GitHub Pages 會自動更新。

**Fork 或自己開一套環境**：才需要照下面整套走一遍，把 `js/config.js` 的四個值
（`SUPABASE_URL`、`SUPABASE_ANON_KEY`、`CLAUDE_PROXY_URL`、`OWNER_EMAIL`）換成你自己的。

> **唯一的真實來源是 GitHub 的 `main` 分支。**
> 網站是從 `main` 部署的，所以「網站現在的行為」等於「`main` 現在的內容」。
> 雲端硬碟裡的資料夾是備份快照，時間點可能比 `main` 舊，**不要拿它當作依據**，
> 也不要把它的內容當成「應該是這樣」——要確認正式站現在是什麼設定，看 `main`。
> 兩邊不一致時，一律以 `main` 為準，備份重新匯出一份就好。

## 上線前要做的事

### 1. 建立 Supabase 專案
1. 到 https://supabase.com 免費建立一個新專案。
2. 左側 **SQL Editor** → New query，貼上整份 `supabase-schema.sql` 並執行。
   這會建立配對專用的 `match_profiles`、`applications`、`match_messages` 並開啟 RLS。舊版若曾
   使用共用的 `profiles`，腳本只搬移兩表共有欄位，不會修改其他產品的 `profiles` 或其政策。訪客只能看到靜態公開頁，
   **沒有登入的人完全讀不到會員與申請資料**；已登入的人也只能看到／修改自己的登記資料，
   以及自己牽涉在內的申請。
3. 左側 **Project Settings → API**，把「Project URL」與「anon public」金鑰
   貼進 `js/config.js` 對應的兩個欄位。

### 2. 開啟 Google 登入（你會自己來加的部分）
前端已經接好一顆「使用 Google 登入」按鈕（`supabase.auth.signInWithOAuth({provider:'google'})`），
你只需要：
1. 到 Google Cloud Console 建立 OAuth 2.0 用戶端（網頁應用程式）。
2. **在那個用戶端裡加入 Supabase 的 callback 網址**（很容易漏掉，漏了 Google 登入會直接失敗）：
   ```text
   Authorized redirect URIs
   https://<你的專案代號>.supabase.co/auth/v1/callback
   ```
   專案代號就是 `js/config.js` 裡 `SUPABASE_URL` 的那一段。
3. Supabase 專案 → **Authentication → Providers → Google**，貼上 Client ID / Secret 並啟用。
4. Supabase → **Authentication → URL Configuration**，把正式網址加進 Site URL 與 Redirect URLs：
   ```text
   Site URL      https://<你的帳號>.github.io/warmsun-adoption-match/
   Redirect URLs https://<你的帳號>.github.io/warmsun-adoption-match/**
   ```

> **第 2 步和第 4 步是兩件不同的事，不要混在一起。**
> 第 2 步（Google Cloud Console）管的是「使用者在 Google 按下同意之後，Google 要把他送回哪裡」
> ——答案是送回 **Supabase**，不是送回你的網站。
> 第 4 步（Supabase）管的是「Supabase 收下之後，再把使用者送回你網站的哪裡」。
> 只設了第 4 步而漏掉第 2 步，Google 會擋在 `redirect_uri_mismatch`，
> 而且錯誤訊息出現在 Google 那一頁，看起來完全不像是自己網站的問題。

5. 完成後不用改任何程式碼，按鈕會自動生效。Email／密碼登入在此之前就能正常使用。
   使用者從受保護分頁開啟 Google 登入時，網站會把原本的目的分頁暫存在同一分頁的
   `sessionStorage`，OAuth 回站後再導回，不會一律跳到佈告欄。

### 3. 開啟 GitHub Pages
Repo 設定 → **Settings → Pages** → Source 選「Deploy from a branch」→ 選 `main` 分支、
`/ (root)` 目錄 → Save。幾分鐘後就能用 `https://<你的帳號>.github.io/warmsun-adoption-match/` 開啟。

### 4. 部署 Edge Functions（兩個必要、一個選用）

專案有三個 Edge Function。**其中兩個是必要的，跟要不要用 AI 完全無關**：

| 函式 | 做什麼 | 沒部署的話 |
|---|---|---|
| `admin-users` | 管理後台的會員管理（限制發文、停用登入、永久刪除會員） | 管理後台那幾顆按鈕會失敗 |
| `delete-account` | 使用者自行刪除帳號（同時處理 Auth 帳號與相關資料） | 「刪除帳號」會失敗 |
| `claude` | （選用）AI 代理 | AI 功能自動停用，其他功能不受影響 |

1. 安裝 [Supabase CLI](https://supabase.com/docs/guides/cli)，登入並連結你的專案：
   `supabase login` → `supabase link --project-ref <你的專案代號>`
2. 部署這兩個必要的函式：
   ```bash
   supabase functions deploy admin-users
   supabase functions deploy delete-account
   ```

> 這兩個以前被寫在「（選用）開啟 AI」底下，很容易讓人得到「我不用 AI，所以整段跳過」
> 的結論——結果連刪除帳號跟會員管理都沒部署，而且是等到真的要用才發現。

### 4b.（選用）開啟 AI 輔助評估
配對站的「診療室」（消耗診療點數的「主治獸醫評估」）與「待認養」後台的「AI 閱讀這份申請」
（免費不扣點）都靠同一個 AI 代理，只需要設定一次：
1. 部署函式：`supabase functions deploy claude`
2. 到 https://console.anthropic.com 申請一組 API 金鑰，並設定正式站來源（不會出現在前端）：
   `supabase secrets set ANTHROPIC_API_KEY=sk-ant-xxxxx SITE_ORIGIN=https://你的正式網域`
3. 把函式網址貼進 `js/config.js` 的 `CLAUDE_PROXY_URL`：
   `https://<你的專案代號>.supabase.co/functions/v1/claude`
4. 留空這個設定，兩個 AI 功能的按鈕都會自動顯示為停用狀態，不影響其他功能。

新帳號預設贈送 5 點診療點數（`match_profiles.credits`）。送出一份認養申請要扣 1 點「掛號費」，
請主治獸醫評估一位申請人要扣 1 點「診療費」；若對方超過 14 天沒處理你的申請，可以在
「我送出的申請」自行退回掛號費。「診療室」裡的儲值方案目前是模擬付款，不會真的扣款——
要串接真的金流（例如綠界、TapPay）需要另外接金流商的後端，目前還沒做。

### 4c. 部署完成後的驗收清單

「照著做完應該就好了」不算驗收。實際跑一遍下面這些，尤其是打勾的那幾項——
它們對應的都是設定漏掉時**不會報錯、只會安靜壞掉**的地方：

```text
登入
□ Email 註冊成功
□ Email 登入成功
□ Google 登入成功                    ← 漏了第 2 步的 callback URI 就會卡在 Google 那頁
□ OAuth 完成後回到原本要去的分頁，不是一律跳回佈告欄

權限
□ 建立登記資料成功
□ 一般會員看不到「管理後台」分頁
□ 管理員看得到並打得開「管理後台」
□ 站長帳號在「我的資料」最下面看得到私人工具連結
□ 其他帳號看不到連結，直接開網址也會被擋在門口
□ 私人工具關掉重開，資料還在（owner_kv 有寫進去）

必要的 Edge Functions
□ 管理後台的「限制發文／停用登入」有作用      ← admin-users
□ 「刪除帳號」跑得完                          ← delete-account

照片
□ 上傳大頭照成功
□ 上傳驗證照成功，審核通過或退回後驗證照被刪掉

AI（選用）
□ 沒設定 CLAUDE_PROXY_URL 時，網站其他功能完全正常，AI 按鈕顯示為停用
□ 設定之後，主治獸醫評估與「AI 閱讀這份申請」都回得了內容
□ AI 的輸出裡沒有任何百分比／分數（見第 34 節）
```

### 4d. 本機開發

**不要用 `file://` 直接開 `index.html` 測登入。** OAuth 的 redirect、
`sessionStorage` 的分頁記憶都需要一個真正的 origin，`file://` 下會失敗或行為不同。
起一個本機伺服器就好：

```bash
python3 -m http.server 8080
# 然後開 http://localhost:8080
```

要測 Google 登入的話，記得把 `http://localhost:8080` 也加進
Supabase 的 **Redirect URLs**（Google Cloud Console 那邊不用改，
因為 Google 永遠只回到 Supabase 的 callback）。

Email／密碼登入、其他所有功能在 `http://localhost:8080` 下都能直接測。
（專案的自動化測試是另一回事——它們用 `file://` 開頁面並攔截掉 Supabase，
不碰真的登入流程，所以不受這一條影響。）

### 5. 大頭照／身分驗證／管理員審核

登記需要上傳大頭照與一張「驗證照」（比指定手勢＋手持代碼紙條，用來確認是本人）。
大頭照存在 Supabase Storage 的公開 bucket，驗證照存在私密 bucket，
**審核通過或退回後系統會立即刪除驗證照**。`supabase-schema.sql` 已經包含建立這兩個
bucket 與對應權限的 SQL，跑過整份腳本就會自動建好，不用另外去 Storage 頁面手動設定。

要能使用「管理後台」（全站統計、檢舉處理、範本主檔管理、照片與驗證照審核台），你要先把
自己的帳號設成管理員（這一步無法從網頁上做，得自己去資料庫改，避免任何人能自封管理員）：
1. 先用你自己的帳號在網站上登入一次（讓 Supabase 的 `auth.users` 裡有這筆帳號）。
2. 到 Supabase **SQL Editor**，執行（記得換成你自己的 email）：
   ```sql
   update public.match_profiles set is_admin = true
   where id = (select id from auth.users where email = '你的帳號 email');
   ```
3. 重新整理網站，頂端分頁會出現「管理後台」，裡面會顯示全站統計、待處理檢舉、範本主檔編輯，
   以及原本的照片／驗證照審核台。

**把站長帳號 `warmsun.shelter@gmail.com` 也設成管理員**，就是同一段 SQL 換一個 email：

```sql
update public.match_profiles set is_admin = true
where id = (select id from auth.users where email = 'warmsun.shelter@gmail.com');
```

有三件事要注意：

- **那個帳號必須先在網站上登入過至少一次**，`auth.users` 裡才會有它。沒登入過的話上面這句
  會「執行成功但影響 0 列」——不會報錯，你會以為設好了，其實沒有。跑完務必確認：
  ```sql
  select u.email, p.is_admin
    from auth.users u join public.match_profiles p on p.id = u.id
   where u.email = 'warmsun.shelter@gmail.com';
  ```
  要看到 `is_admin = t`。查不到任何一列就代表那個帳號還沒登入過。
- **管理員跟站長是兩件不同的事。** `is_admin` 決定看不看得到「管理後台」；
  `js/config.js` 的 `OWNER_EMAIL` 決定看不看得到私人工具。
  兩者互不影響——可以有好幾個管理員，但私人工具永遠只有 `OWNER_EMAIL` 那一個帳號。
- **這一步只能從資料庫做，不能從網頁上做**，而且是刻意的：
  `is_admin` 被寫入防護 trigger 擋著（見第 7 節），任何人在 devtools 裡呼叫
  `DB.saveMyProfile({is_admin:true})` 都會被還原。

大頭照的系統初檢一樣透過 Claude 代理（見第 4b 步），沒設定 `CLAUDE_PROXY_URL` 也不會擋住
註冊流程，只是會略過初檢、直接進人工審核。

### 6. 私人工具（`shelter-review-assistant.html`）

這個工具只給站長本人使用，跟平台其他會員的資料完全分開：
1. 站長帳號寫在 **`js/config.js` 的 `window.OWNER_EMAIL`，只有這一個地方**。
   `index.html` 與 `shelter-review-assistant.html` 都讀它，不用同步兩份。
   沒設這個值的話兩個頁面都會直接關門（連結不出現、工具進不去），不會退回任何預設帳號。
2. 用這個帳號登入 `index.html` 後，到「個人中心 → 我的資料」最下面會看到
   「小橘的 Dcard 企劃工具（僅本人可見）」連結，點進去就是 `shelter-review-assistant.html`。
3. 直接用同一組帳密登入即可，資料存在 `owner_kv` 資料表
   （`supabase-schema.sql` 已經建好表格與 RLS 政策）。用別的帳號登入會被擋在門口。

> **`owner_kv` 的保護實際上是什麼，值得講精確一點**，不然下一個維護的人會誤會。
>
> RLS 政策是 `auth.uid() = owner_id`，意思是**每個登入的會員都可以讀寫「自己的」
> `owner_kv`，但讀不到別人的**。資料庫層面**沒有**一份「只有某個 email 能用」的白名單。
>
> 所以「只有站長能用這個工具」是兩層合起來的結果：
> **前端閘門**（`user.email === OWNER_EMAIL`，決定誰進得去這個頁面）
> ＋ **資料庫隔離**（`auth.uid() = owner_id`，決定誰讀得到站長的資料）。
>
> 對現在的目標這樣已經夠了——就算有人繞過前端直接呼叫 `DB.ownerKvSet()`，
> 他也只會寫進**他自己的**那一份，碰不到站長的任何資料。
> 但要知道 RLS 不會說「你不是站長所以拒絕」，它只說「你不是這筆資料的主人」。
4. 這個工具裡產生審查草稿一樣透過 Claude 代理（見第 4b 步），沒設定 `CLAUDE_PROXY_URL`
   的話會顯示「尚未設定 AI 代理網址」，但存檔、罐頭回覆、名冊等其他功能不受影響。

### 7. 安全性補強：擋掉自己改自己權限／點數的漏洞

早期版本的 `profiles_update_own` 只檢查「改的是不是自己那一列」，沒檢查「改的是哪一欄」——
任何登入的人在瀏覽器 devtools 執行 `DB.saveMyProfile({is_admin:true, credits:999999})` 就會直接成功。
`supabase-schema.sql` 第 9 節已經補上防護（trigger 擋住 `is_admin`／`credits`／`credit_log`／
`bonus_given` 被非管理員直接改，也擋住自己把 `photo_status`／`verify_status` 設成 `approved`），
並把掛號費、診療費、退款、加點都改成專用的 Postgres 安全函式（`apply_to`、`spend_credits_for`、
`refund_application`、`admin_add_credits`），前端不再能直接改點數欄位。

**如果你的 Supabase 專案是舊版本、已經在跑了**，重新貼一次整份 `supabase-schema.sql` 執行即可
（跟之前每次補欄位一樣，是安全的重複執行，不會動到既有會員資料）。這次也把「診療室」的模擬
儲值按鈕拿掉了（自己給自己加點本身就是同一種漏洞的 UI 版），改成「線上儲值尚未開放，請洽站方
人工加值」，管理員可以到「管理後台 → 手動加點」幫指定會員加點——這是目前唯一合法的加點入口
（送出申請的掛號費、逾期退款、AI 診療費用扣點則都各自走專用安全函式，使用者自己不能繞過）。

真的要接金流（例如綠界 ECPay）時，`admin_add_credits` 的邏輯可以直接被金流回調的 Edge Function
重用（用 service_role 呼叫、訂單編號當 `ref` 防止重複回調），不用整套重寫。

### 8. 病歷卡與物種擴充

佈告欄上的每一份登記會排版成一張「動物病例表」：病例號碼、基本資料、行為觀察、健康與性格
星等（親人程度／活動量／慢熱程度／作息規律／獨立程度）、個性標籤、最喜歡的事、禁忌事項、
認養資格、健康告知、主治獸醫備註。

- **物種從 2 種擴充到 13 種**（貓咪、狗狗、兔子、刺蝟、倉鼠、天竺鼠、鸚鵡、蜜袋鼯、烏龜、
  變色龍、鬥魚、金魚、孔雀魚），而且**性別獨立成一個欄位**，不再是「貓＝女生、狗＝男生」。
  重跑 `supabase-schema.sql` 時會自動幫既有會員補上性別（依舊規則：貓→女生、狗→男生），
  現有資料不會消失。
- **分階段揭露**：生日要對方送出第一階段申請後才看得到；健康告知可以自己選擇「直接公開／
  對方送出第一階段申請後／進入第二階段後」才揭露。
- **進階診斷（3 點）**：收到申請後，可以請主治獸醫讀完對方第一階段的回答，針對講得含糊或
  可能有落差的地方，客製 4～6 題第二階段問題。擬好的題目會寫進這筆申請的
  `a2_questions`，通過第一階段時會直接沿用，不會被你的題庫蓋掉。

### 9. 申請內容改成真的付費解鎖、答題紀錄、送出前的同意關卡

之前「看第一階段詳細回答要付點數」只是說法，答案其實跟其他欄位一起存在 `applications`，
收件方本來就讀得到整列，前端遮住沒有用（打開 devtools 就能看到）。這次把回答搬到獨立的
`application_answers` 表，RLS 規定申請人永遠看得到自己的，收件方要付費解鎖（`unlock_a1`，
1 點）才看得到；發第二階段問卷也要付費（`send_stage2`，2 點）。**這是一次會動到既有資料的
搬遷**：重貼 `supabase-schema.sql` 時，既有申請的答案會自動搬進新表，並且全部標記成「已解鎖」，
不會回頭跟人收錢；同時原本 `applications.keeper_note`（飼主私人筆記）也搬進獨立的
`application_private_notes` 表並修掉了一個已知缺陷——之前收件方技術上讀得到對方的私人筆記，
現在 RLS 保證只有寫的人自己看得到。

- **我的答題紀錄**：送出申請或第二階段回答時，答案會自動存進你自己的 `match_profiles.answer_bank`。
  下次填寫申請表遇到相似題目，題目下方會展開「你以前答過的」，可以一鍵帶入或附加在後面，
  再依這次的題目調整。比對用題目文字的相似度，不透過 AI（不用額外扣點，速度也快）。
- **申請前的同意關卡**：點「提出認養申請」後，會先看到告知事項（誰看得到你的回答、要付費才
  能調閱、會存進答題紀錄等），勾選同意才會出現題目，同意時間記在這筆申請的 `consent_at`。
- 跟原本一樣，`applications` 也補上了同一種欄位層級的防護——收件方不能自己把 `stage`／
  `a1_unlocked`／`stage2_paid` 改成已解鎖來白嫖，只能透過會扣點、會驗證的安全函式操作。

### 10. 第三階段解鎖改成申請人付費、收件方免費同意

通過三階段審查後，原本雙方都要各自免費按「同意解鎖」才會互相看到日常觀察資訊。現在改成
**申請人要付 3 點**（`unlock_stage3`）才算完成自己這邊的同意，**收件方那邊維持免費**
（`consent_unlock_to`）——兩邊都同意了才會互相看到，維持原本互相同意的精神，只是申請人這邊
多一道付費關卡。申請人一登入，只要有申請進入第三階段但還沒付費解鎖，頂部會出現提醒橫幅，
「個人中心」的「我的申請」分頁也會顯示 🔔 提醒數字（目前沒有 email／推播通知，僅登入後在頁面
提示）。

寫這段時發現 `unlock_from`／`unlock_to` 這兩欄之前也沒有欄位層級防護——因為
`applications` 的更新政策是整列層級，申請人或收件方其實可以直接把「對方」那一欄也設成
`true`，等於幫對方蓋章同意，不需要對方真的按下同意。這次一併把這兩欄鎖進第 9 節那個
guard trigger，只能透過上面兩支安全函式改。

### 11. 健康告知改成自願勾選、認養申請多一頁領養切結書

「病歷卡」的健康告知原本是一個自由填寫的文字框，現在改成參考健檢報告分類、
自願勾選的核取方塊（心血管疾病、糖尿病／高血壓／痛風、肝功能異常／B肝帶原、氣喘或
呼吸道疾病、遺傳性疾病史、精神性疾病、早產兒、愛滋病、BMI超標、體脂肪過高、不孕、
舊傷、已長期服藥或治療控制中），一項都不勾也可以直接送出，完全由本人決定要不要公開；
文字框保留下來當作「其他補充說明」，寫想額外說明的細節。原本「什麼時候讓對方看到」的
設定不變，仍然是本人自選。新增 `match_profiles.health_tags`（jsonb 陣列）欄位存勾選結果。

送出認養申請時，原本填完第一階段問卷就直接送出，現在中間多一頁「領養切結書」：列出
承諾事項與領養宣言，代名詞會依對方的性別自動換成「他」或「她」，並要求在「認養人」欄位
簽下暱稱才能真正送出申請（送出前都可以按「上一步」回去修改回答）；「認養日期」與
「獸醫核章」由系統自動帶入，不需要手動填寫。這一頁只是送出前的最後確認關卡，內容不會
存進資料庫。

### 12. MBTI 改成下拉選單、後台改成跟前台同一套視覺語言

自我介紹的 MBTI 欄位原本是自由輸入，改成 16 種類型的下拉選單，避免打錯或格式不一致。

`dashboard.html`（我的後台）與 `shelter-review-assistant.html`（面談紀錄室）原本各自有一套
配色（白底＋橘色、IBM Plex Mono 等寬字），跟前台 `index.html` 的紙灰底、金褐色、
Cormorant Garamond／Lora 完全是兩回事。這次把兩個後台頁面的顏色與字體換成跟前台同一套：
紙灰背景、金褐主色、標題字體、圓角與間距系統都對齊，卡片改成白底圓角加淺陰影，輸入框底色
用前台的紙灰色，放在一起不會覺得是兩個網站。

後台跟前台的差異保留三處，都是「同一家店的員工出入口」的感覺：頂欄改成深墨底＋金色標題＋
底部金褐線；分頁選中時背景是深墨色而不是金色（前台用金色標示「你在看這個」，後台用墨色
標示「你在管理這個」）；登入畫面整片深墨、標題金色，副標改成「管理端　請輸入通行碼」。
字級也一併從 12～15px 拉到 16px 以上，跟前台一致。

面談紀錄室裡那個旋轉的紅色印章（`.stamp`）刻意保留原樣沒有動——那是後台最有個性的元素，
蓋章本來就該是紅的，換成金色反而弱掉。

### 13. 後台配色改成暖陽動態漸層、加碼照片、快速邀請

第 12 節做的深墨頂欄／登入畫面被覺得太重、不像「暖陽」，改成會慢慢流動的金色漸層
（`--sun-1`／`--sun-2`／`--sun-3` 三段色，`sunshift` 這個 `@keyframes` 讓漸層每 18 秒緩緩
移動一次，`prefers-reduced-motion` 會關掉動畫）；分頁選中的樣式也從「深墨底」改成「實心
金褐底＋白字」，跟前台的淺色 outline 樣式做出區隔，但整體色溫回到暖色系。

**加碼照片**：登記人可以在「我的登記」多傳兩張照片——第一階段（口罩照或側拍照）、第二階段
（生活照），全部選填。這兩張不是公開的，存在私密的 `stage-photos` bucket，storage 的
RLS 政策會檢查申請人跟這個登記人之間的申請進度：進到第二階段（`stage >= 2`）才看得到
第一階段那張，進到第三階段（`stage >= 3`）才看得到第二階段那張，讓申請人有「通過審查、
解鎖回饋」的感覺。`match_profiles.stage1_photo`／`stage2_photo` 兩個布林欄位只是「有沒有上傳」
的旗標，不是照片本身。

**快速邀請**：登記人可以勾選「開放快速邀請」。申請人先透過 `request_fast_track` 送出邀請，
此時不扣點也不解鎖；只有登記人透過 `accept_fast_track` 明確接受後，系統才扣申請人 10 點、
把申請推進第三階段並讓雙方解鎖。任一方未同意就維持正常審查流程。這 10 點會轉給登記人，
但限 14 天內用完——`match_profiles.bonus_credits` 記錄每一筆
獎勵點數的到期時間，到期還沒花完的部分會被 `settle_bonus_credits()` 收回（用「還剩多少
可花」去扣，不會扣到負的）。因為沒有排程系統，改成「順手結算」：登入後會呼叫一次，其他
會扣點的安全函式（`spend_credits_for`／`apply_to`／`unlock_a1`／`send_stage2`／
`unlock_stage3`）開頭也都會先結算一次，盡量不要讓過期的點數一直掛在帳上又被拿去花用。
`applications.fast_invite_from`／`fast_invite_to` 記錄雙方同意，`skipped` 記錄是否已完成快速邀請，讓兩邊畫面都
能顯示對應的說明文字，而不是誤判成「還沒填問卷」。

`bonus_credits`／`skipped`／`allow_skip` 的欄位層級防護：`allow_skip` 是本人自由決定的
一般設定，可以直接改；`bonus_credits`（會影響未來能不能被扣回）跟 `skipped`（跟
`stage`／`unlock_from` 一樣是審核流程狀態）都鎖進第 9、11 節那兩個 guard trigger，只能
透過 `request_fast_track`／`accept_fast_track`／`settle_bonus_credits` 這些安全函式改；舊版
`skip_to_unlock` 已停用，避免單方付款替另一方表示同意。

這幾個機制都先在本地真的 Postgres 16 上驗證過：付款後雙方點數與到期時間正確、點數不足會
擋下、對方沒開放一鍵通關會擋下、直接 `update` 偽造 `stage`／`skipped`／`bonus_credits`
會被 trigger 打回原值、到期收回會用「剩多少扣多少」不會透支、陌生人與進度不夠的申請人都
讀不到別人的加碼照片，進度夠了才讀得到對應那一張。

### 14. 後台配色改回「線條，不是色塊」

第 13 節的暖陽漸層被覺得太濃重——回頭看附件那份 Classical 設計系統（這個站的字體、
配色從一開始就是照著它做的）才發現自己違反了它最基本的原則：色彩只當邊框、細線、文字用，
大面積一律留白／留紙灰，「不要用實心色塊填滿卡片或按鈕」。連它範例裡的管理員模式，都只是
同一個頁面切一個分頁，長得跟其他分頁一模一樣，完全沒有特別上色。

所以把第 12、13 節做的頂欄底色、登入畫面底色全部拿掉，改回跟前台一樣的紙灰背景；後台跟
前台現在只剩兩個很輕的差異：頂欄下緣是金褐色的線（前台是無色細線），分頁選中的底色用
`color-mix(in srgb, 主色 14%, transparent)` 上一層極淺的金褐色調（前台本來就有的
`--brand-tint` 也是同樣邏輯，只是再淺一點點）。真正拿來分辨「這裡是員工入口」的是
STAFF AREA／CASE FILE 這種 outline 標籤和「管理端」的文案，不是靠色塊。

### 15. 前台首頁改成公開的介紹頁，登入／註冊搬到右上角

`index.html` 原本一進站就是整片登入畫面（`#gate` 蓋住全部內容），現在改成一進站先看到
公開的「首頁」分頁——一段介紹文字、三階段流程卡片、「查看佈告欄／開始登記」兩個按鈕，
不需要登入就看得到。登入／註冊改成右上角兩個小按鈕，點了才彈出一個置中的小視窗（原本的
`#gateForm` 整組搬進去，功能不變），背景變暗但首頁內容還在後面，點視窗外或右上角的 ×
都能關掉。

分頁分成兩種：「首頁」「流程說明」「隱私權」不需要登入，任何人都看得到；「佈告欄」
「個人中心」「管理後台」需要登入，未登入時點下去（或按首頁的「查看佈告欄」／「開始登記」）
會彈出登入視窗，記住你原本想去哪個分頁，登入成功後自動帶你過去；如果只是單純按右上角
「登入」，成功後預設帶去佈告欄。原本在受保護分頁時登出，會自動跳回首頁，不會停在一個
突然變成空白或報錯的畫面。

`dashboard.html`／`shelter-review-assistant.html` 維持原本一進去就要登入的設計沒有動——
那兩個本來就是「登入後台」的工具，不是給訪客看的行銷頁面。

### 16. 安全性補強、對話功能、身高體重、AI 匹配度、會員管理、AI 圖片規則

這次已正式套用至生產 Supabase；`supabase-schema.sql` 保留為可重跑的完整結構與遷移來源。

**安全性補強**：配對會員改用獨立的 `match_profiles`，不再把另一個產品的 `public.profiles`
當公開會員目錄。公開卡片改由 `get_visible_match_profiles()` 依申請階段遮罩敏感欄位；申請、
點數、階段推進、快速邀請與發訊息都由資料庫函式驗證身分、狀態與額度。`apply_to()` 也會在
伺服器端阻擋重複申請，檢舉則限制同一組人同時只能有一筆未結案紀錄。

**對話視窗（第二階段開放）**：訊息綁定在單一申請的 `match_messages`，只有申請雙方能讀取，
管理員可因檢舉稽核；發訊息需帳號仍有效、未被限制發文、申請已進第二階段且聊天室未關閉。
訊息函式包含長度限制與頻率限制，也可傳送「客製問題」類型。

**身高（必填）／體重（選填）**：身高不太會變，體重會因為各種原因改變，所以只有身高列為
必填欄位，沒填會擋下儲存；體重維持選填，佈告欄卡片上「有填才顯示」。

**主治醫師 AI 診斷加上匹配度**（❌ 已在第 34 節整個移除：AI 不再輸出任何百分比，
`applications.vet_scores` 也已經從 schema 裡刪掉）：這一版曾經請 AI 在回覆第一行給一個
「匹配度：XX%」，畫面上還把那一行獨立標示出來。那個數字沒有校準基礎，卻長得最像結論——
留著它，使用者會拿它當答案，而不是拿它當一份要自己讀完的資料。

**管理後台：會員管理**：管理員可限制或恢復發文、停用或恢復登入，以及永久刪除會員。這些
操作經 `admin-users` Edge Function 驗證管理員身分；永久刪除會同時處理 Auth 帳號與相關資料，
不再只是刪除公開登記。

**AI 生成照片規則**：使用者需選擇本人照片或 AI 形象照；AI 形象照必須聲明與本人高度相似，
並以私密真人驗證照人工核對，預估七個工作天，本人照片預估兩個工作天。95% 是使用者聲明與
人工審核準則，不宣稱系統已用生物辨識精確量測。

### 17. 會員管理：修掉「點了沒反應」的靜默失敗、加上檢舉直接封鎖

「永久刪除」「停用登入」這類操作都會先跳出 `confirm()` 再跳出 `prompt()` 問處理原因；
原本如果這第二個輸入框被留空或按取消（`prompt()` 回傳空字串或 `null`），程式碼會直接
`return`，畫面上什麼提示都沒有——在管理員看來就是「按了沒有用」。現在兩種情況都會跳出
明確的提示（「已取消，尚未執行」／「沒有填寫原因，尚未執行」），不會再無聲失敗。

原本「檢舉處理」清單只能「標記已處理」或「移除該登記」，沒有辦法針對辱罵、嘲諷這類重大
違規直接封鎖帳號，只能先跳到下面的「會員管理」清單裡自己找人。現在每筆待處理檢舉旁邊多了
「永久封鎖（停用登入）」按鈕，可以直接從檢舉內容審核、輸入原因後永久停用對方登入
（沿用既有的 `suspend` 動作，Supabase Auth 端設定 100 年的封鎖天數，等同永久且無法再用
同一帳號登入），跟「永久刪除」不同的是不會把登記資料、對話紀錄一起銷毀，方便之後查核。

如果按下「永久刪除」「停用登入」等按鈕後跳出「操作失敗」，最常見的原因是 `admin-users`
這支 Edge Function 還沒部署（見上面第 4 步），或是還沒設定 `SITE_ORIGIN` 密鑰導致 CORS
被擋下——這兩個都需要你自己用 Supabase CLI 執行一次，不是網頁重新整理就能解決的。

### 18. 學歷欄位、管理後台分頁隱藏、通知鈴鐺、主治獸醫備註 AI 生成

**學歷（選填）**：「我的資料」新增一個學歷下拉選單（高中職以下～博士），跟職業放在一起，

**一般會員看不到「管理後台」分頁**：以前分頁列固定列出全部分頁，非管理員點進去只會看到

有這個功能。現在分頁列會依登入者是否為管理員動態決定要不要顯示這個按鈕。

**修掉「退回審核後，本人完全不知道、原因也看不到」的問題**：原本審核退回的原因只是寫在
`photo_reason`／`verify_reason` 這兩個欄位，畫面上要自己點進「我的資料」才看得到；而且
一旦重新上傳照片準備再審一次，這兩個欄位會立刻被清空，原本的退回原因就這樣消失了——

`--warn` 左側色條）特別標注、跟一般會員傳來的訊息通知區分開；點一則通知會標記已讀、未讀

新訊息／新審核結果都是即時推播（Supabase Realtime），不用重新整理頁面。

**主治獸醫備註加上 AI 生成**：這個放在病歷卡最下方的一句話，之前只能自己手動打。現在

### 21. V0.2（一）：點數制度重新定義、拿掉「付錢跳關」

一次外部產品審查指出：功能已經夠多，真正的問題是**資訊架構、隱私層級與商業規則開始互相打架**。
這一節與下一節就是照那份審查整理出來的 V0.2，先不加新功能、把現有的東西整理乾淨。

**點數說明與服務條款自相矛盾**：點數頁列出掛號費 1 點、解鎖 3 點，服務條款卻寫「核心流程
（登記、瀏覽、提出申請、回答問卷、審查、解鎖）皆可免費使用」——兩個版本不可能同時成立。
現在重新定義成：**免費的是「建立關係」，收費的是「效率與 AI」**。

- 掛號費改成**每 7 天內前 3 筆申請免費**，超過才收 1 點（`apply_to` 用滾動 7 天視窗計算）
- **解鎖第三階段改成完全免費**——都通過三階段審查了還要付錢才能聯絡，本來就說不過去
- 付費項目只剩：超額申請、第二階段出題、主治獸醫評估、進階診斷、AI 生成備註、優先邀請

**拿掉「付錢跳關」**：舊版「快速邀請」是付 10 點直接跳過全部三階段審查，而且那 10 點會轉進
對方帳號。這跟平台主打的「慎重不是門檻，而是尊重」直接衝突，看起來就是課金插隊；點數進到
對方帳戶更接近「有人花錢買我的注意力」，甚至有打賞／競價的觀感。整個移除，改成
**優先邀請**（`send_priority_invite`，3 點）：只在對方收件匣多一個優先標記、附一封最多 300 字的
邀請信，**不跳過任何審查階段**，點數留在平台、不會轉給任何一方。登記表上的「開放快速邀請」
勾選框一併移除；舊資料的 `skipped`／`fast_invite_*` 欄位保留，讓既有申請還顯示得出來。

### 22. V0.2（二）：公開資料改成四層漸進式揭露

這是這輪最重要的一項。原本的設計自相矛盾：產品哲學說「資訊要逐步解鎖」，但實際上只要通過
審核，任何登入會員一打開病歷卡就看得到**年收入、婚姻、有無孩子、兵役、居住狀況、負債、
生育規劃、工作時數**——資訊量比一般交友軟體還多。現在改成四層：

| 層級 | 開放時機 | 看得到什麼 |
|---|---|---|
| 第 0 層 | 佈告欄（還沒有申請關係） | 暱稱、物種性別、**年齡區間**、地區、職業、自我介紹、個性標籤、最喜歡的事、禁忌、星等、關係期待、興趣、個性、MBTI、擇偶條件 |
| 第 1 層 | 對方送出第一階段申請後 | 精確年齡、身高、體重（另由本人決定公不公開）、學歷、婚姻、有無孩子、兵役、生活習慣 |
| 第 2 層 | 進入第二階段後 | 年收入區間、居住狀況、生育規劃、一週工作時數 |
| 第 3 層 | 雙方都同意解鎖後 | 生日、日常觀察資訊（社群帳號等） |

**負債狀況與健康告知**的揭露時機完全由本人自己決定（直接公開／第一階段後／第二階段後／
**永遠不公開**），新增 `debt_when` 欄位，兩者都多了「永遠不公開」這個選項。

**年齡在第 0 層只給區間**（25 歲以下、25～29、30～34⋯⋯），新增 `age_bucket()` 函式處理；
通過第一階段後才顯示精確歲數。生日也從原本的「第一階段後」往後移到「雙方同意解鎖後」。

實作上**遮罩是在資料庫端做掉的**（`get_visible_match_profiles()`），未達條件的欄位在傳輸階段
就已經被移除，不是只有畫面上遮起來——打開 devtools 也看不到。函式另外回傳 `rel_stage` 與
`rel_unlocked`，前端只負責把「還沒開放」畫成鎖頭提示。佈告欄卡片、首頁示意卡片、登記表說明、
流程說明與隱私權政策的蒐集項目全部同步改寫成四層版本；「詳細資料」摺疊區也把已經歸到第一／
第二層的欄位拿掉，否則漸進式揭露會被那個區塊整個繞過。

**過程中抓到一個自己造成的真 bug**：`isApproved()` 除了照片與驗證照狀態，還多檢查一個
`!!p.height_cm`（那是身高還必填的年代留下來的）。身高改選填後這個檢查本來就不對，加上第 0 層
的 `height_cm` 一律被遮成 null，結果是**還沒申請過的人通通從佈告欄消失**。已經拿掉這個條件。
這也是為什麼分層測試要真的去讀畫面文字：第一次跑的時候「不該看到的都看不到」全部是綠的，
但其實是因為整個佈告欄根本是空的，屬於假通過。

驗證：四層揭露在真的 Postgres 16 上逐層驗證過——第 0 層只給年齡區間、第 1／2 層各自只開放
該層欄位、第 3 層要**雙方都同意**（只有單方解鎖時生日與社群仍然是 null）、`debt_when` 與
`health_when` 設成 `never` 時即使到第 3 層也永遠不給、本人讀自己的資料則完全不受遮罩影響。
前端另外寫了一份 `smoketest-tiers.js`，把資料庫的遮罩邏輯照抄一份，逐層檢查畫面上「該看到的
看得到、不該看到的看不到」共 34 項，全部通過。

### 23. V0.2（三）：首頁重新分層、登記表改成五步精靈

**首頁一次塞太多東西**：原本第一屏就要同時消化品牌介紹、三階段卡片、示意卡片與註冊引導，
第一次來的人很容易不知道該按哪裡。現在第一屏只留一句話與兩個動作：

> **不滑卡。先好好認識，再決定要不要靠近。**
> 暖陽不保證你遇見對的人，但希望讓你少把時間留給錯的人。
> ［看看誰在等家］［建立我的病歷卡］

往下才依序是「怎麼運作」（四個 STEP，用**排除漏斗**的角度寫：先確認基本相容、再談價值觀與
溝通、最後才看有沒有心動）、示意病歷卡、以及最後的行動呼籲。頁首那段長副標與「這是配對原型
的公開站」公告在首頁上會變成同一件事講兩次，所以**只在首頁**收起來，其他分頁維持原樣。

**登記表改成五步精靈**：原本四十幾個欄位一次全部攤開，手機上尤其容易放棄。現在拆成
「1. 你是誰／2. 照片與驗證／3. 自我介紹／4. 分階段資料／5. 希望遇到誰」，一次只顯示一段，
上方有步驟列可以直接跳，也可以用上一步／下一步走。

幾個刻意的設計：

- **「儲存登記」永遠看得到**，不必填到最後一步才存得起來；第一次登記只要填完第 1、2 步就能送審
- 第 4 步照四層揭露重新分組（第一階段後開放／第二階段後開放／由你自己決定開放時機／
  佈告欄就看得到），讓人在填的當下就知道這個欄位什麼時候會被誰看到
- 生日移到第 4 步最後，標示「雙方同意解鎖後才會顯示」，跟實際行為一致
- 手機上步驟列只留編號（1. 2. 3. 4. 5.），桌機才顯示完整標題
- 換步驟時自動捲回表單頂端，不會停在上一段的中間

**測試工具的教訓**：跑回歸時我原本用 `grep -c '❌'` 判斷通過與否，結果 `smoketest-round4.js`
其實是**因為找不到已經被移到第 4 步的欄位而逾時崩潰**，一個 ❌ 都還沒印出來就死了，卻被判成
「0 failures」。已經改成一支會同時檢查 exit code、✅ 與 ❌ 數量的 `runall.sh`，崩潰會明確標成
💥 而不是靜悄悄地變成綠燈。

### 24. V0.2（四）：安全中心

安全規範原本只寫在服務條款裡，但真正需要它的時候不會有人去翻條款。這一節把它從「文件」
變成「產品功能」。

**新增「🛡️ 安全中心」分頁**：第一次見面的六項建議（公共場所、自行往返、告知親友、不提供
住址、不借貸不代收款、不舒服可以直接離開）、封鎖與檢舉各自能做到什麼、以及自己的封鎖名單
管理。也列出 110 與 113 專線——平台自己處理不了的事，要讓人找得到真正該找的單位。

**使用者層級封鎖**（新的 `match_user_blocks` 表）：跟原本「關閉單一對話」的 `match_blocks`
不同，這是「我完全不想再看到這個人，也不想被他看到」。封鎖後：

- 雙方都不會再出現在彼此的佈告欄（**單向封鎖即雙向隱藏**，避免被封鎖的人還能一直看對方）
- 既有對話立即關閉，對方無法再傳訊息
- 對方無法再對你提出申請
- **對方不會收到通知**，RLS 也保證他查不到是誰封鎖了他（避免報復）

封鎖入口放在佈告欄卡片與對話視窗兩個地方——會需要封鎖的時候，人不會想先去翻設定頁。
新增名單一律走 `block_user()`，前端拿不到 insert 權限，因為封鎖同時要連帶關閉既有對話。

**交換聯絡方式前的安全檢查清單**：這是整個流程風險最高的一步，所以按下解鎖時會跳出六項
檢查清單，**六項全部勾選**才能按下「我已確認，解鎖聯絡方式」。而且這不只是畫面上的關卡——
`unlock_stage3()` 與 `consent_unlock_to()` 都多了一個 `p_safety_ack` 參數，沒帶 `true` 伺服器
直接拒絕，繞過畫面直接打 RPC 一樣過不了。舊的單參數版本有明確 `drop`，不會留下一支可以
繞過確認的覆載。

**進第三階段前的溫柔確認**：收件人按「通過，進第三階段」時，會先問一句

> 你現在是**真的想繼續認識這個人**，還是只是不好意思拒絕？
> ［想繼續 ❤️］［先停在這裡也沒關係］

把「其實不想繼續」變成一個可以直接按下去的選項，而不是只能硬著頭皮往下走。按「先停在這裡」
會走原本的婉拒流程（一樣可以留話）。這句話本身就是整個產品想說的事：沒有走到最後也是好結果。

驗證：封鎖行為在真的 Postgres 16 上驗證過——封鎖前看得到、封鎖後雙向都看不到、被封鎖的人
查不到任何封鎖紀錄（`count = 0`）、被封鎖後無法提出申請、解除封鎖後恢復正常。安全確認也
逐項驗證：`p_safety_ack` 沒帶時被擋下並回「請先閱讀並確認安全提醒」、帶 `true` 才成功、
舊的單參數覆載確實已經不存在。前端另寫 `smoketest-safety.js` 共 19 項（含「只勾一部分時
按鈕仍然停用」與「呼叫時確實帶了 p_safety_ack=true」），全部通過。

### 25. V0.2（五）：雙層語言、AI 照片改用可觀察的標準、刪除資料的說法對齊實作

**雙層語言（病歷卡／個人資料卡並存）**。收容所比喻是這個站的識別，但第一次來的人看到
「掛號費」「主治獸醫評估」會不知道自己在買什麼。做法不是把比喻拿掉，而是讓兩種說法並存：

- 流程說明頁最上面加一張**名詞對照表**（8 條），一邊是站上的說法、一邊是實際上是什麼。
- **訪客會先看到的地方（首頁、masthead）用日常說法**，比喻放在括號裡——訪客還不知道比喻。
- **會花到錢的地方（點數頁）一律日常說法在前**，站內用語放括號：
  「AI 配對分析（主治獸醫評估）」「AI 幫你客製追問（進階診斷）」。
- 卡片上的「待認養／飼主」保留收容所用語，但補上 `title`，滑過去（與輔助技術）讀到的是
  「想被認識的人／想主動認識人的人」。
- 真實人生的欄位（健康告知、負債、生育規劃）維持平常說法，不套獸醫比喻——那些欄位是拿來
  做人生決定的，不該讓人覺得自己在被寵物評鑑。

**AI 照片不再要求「相似度 95%」**。那個數字沒有客觀依據，我們沒有也不打算用生物辨識去量
一張圖跟本人有幾分像，寫在切結書裡只是讓人隨便勾。改成一個**可觀察的標準**：「能合理反映
我目前的外貌，見面時對方不會認不出我」。AI 初篩的提示詞也一併改掉，明確要求它**不要**判斷
像不像本人——那件事由人工比對私密驗證照決定。卡片標示簡化為「✨ AI 形象照」。

**刪除資料與保存期限的說法對齊實作**。原本隱私權政策寫「點數與交易紀錄依會計法規保存
五年」，但 `delete-account` Edge Function 實際做的是刪掉 storage 物件之後直接
`auth.admin.deleteUser()`，FK 連鎖把所有資料一起帶走——政策寫的跟程式做的不一樣。既然目前
**線上儲值還沒開放**，帳上只有贈送與人工加值、沒有任何金流紀錄，就照實寫：**會隨帳號一併
刪除**；等真的開放付費，再改成「與個人身分脫鉤後另行保存」並更新說明。「你的權利」與兩個
刪除確認視窗也一起改成「連登入帳號本身一起刪除」。

### 26. V0.2（六）：病歷卡視覺重做、手機版 UX

舊卡片把四十幾個欄位攤平成等寬的點線列，三個上鎖區塊各佔一大塊虛線框，手機上一張卡要滑

### 27. 主治醫師初診規則庫 ＋ 申請者 CRM 的資料規格

這一節只有文件、沒有程式：[`docs/screening-crm-spec.md`](docs/screening-crm-spec.md)。
內容是 `screening_rules` / `screening_results` 的資料格式、CRM 狀態機，以及 58 條初診規則
逐條對到現在資料庫真的存在的欄位。

盤點結論：**58 條裡 11 條現在就能實作、6 條是「禁止觸發」的原則（不需要資料，只需要測試）、
41 條要先補欄位**。缺的欄位集中在四個題組加一個貫穿全部的 Dealbreaker 嚴重度——沒有嚴重度，
所有 🔴 都做不出來，只能全部降級成 🟡。投報率最高的單一欄位是 `weekly_work_hours`：
現在的 `work_hours` 是自由文字（「例：45 小時」），改成數值欄位一個就解決 R001–R005 五條。

規格裡另外釘了四個架構決定：

- **初診在資料庫端跑，回傳只有燈號**——它要讀雙方的完整資料才能比對，但那些值不能傳到前端，
  否則四層漸進式揭露就被繞過去了。
- **還沒提出申請時只給數量**（🟢 8 項 🟡 3 項 🔴 1 項 ⚪ 6 項）。第 0 層直接寫
  「🔴 生育規劃衝突」等於洩漏對方的 `kids_plan`，而第 0 層連精確年齡都看不到。
- **🚨 安全事件完全不進一般初診**，只寫管理後台，被標記的人不會知道，效果是提高人工審查
  順序而不是自動處分。
- **禁止規則要能擋下部署**：R047–R054（MBTI／身高／體重／學歷／收入／年齡差／健康資料
  不得產生燈號）存成 `outcome='never'`，引擎啟動時檢查沒有任何規則引用到這些欄位，
  違反就拒絕啟動。寫在註解裡的約定大家都會忘記，寫成會失敗的檢查才有效。

CRM 那邊的好消息是看板九格裡有七格**完全可以從現有欄位算出來**，只要新增
`opened_at` / `last_activity_at` / `closed_reason` / `crm_tags` 四個欄位加一張
`application_events` 時間軸表。

### 28. 主治醫師初診上線（規格第 1、2 步）：規則引擎、禁止規則、weekly_work_hours

規格見 [`docs/screening-crm-spec.md`](docs/screening-crm-spec.md)，這一節把第 1、2 步做完了。
**免費、規則式、API 成本 NT$0。**

**一個欄位換五條規則**：`weekly_work_hours smallint`。原本的 `work_hours` 是自由文字
（「例：45 小時」），規則沒辦法可靠解析「約 40-50」「看情況」。表單改成數值輸入，
`work_hours` 留著當顯示用，舊資料會自動回填（只取第一個數字，而且只在 1–168 這個合理範圍內才寫）。

**規則是資料，不是程式**：`screening_rules` 一張表 ＋ 一個小型 JSON 條件式直譯器
（`all`/`any`/`not` ＋ `field`/`op`/`value`）。加第 59 條規則不用改前端、不用重新部署。
目前塞了 14 條會動的規則（R001–R005 工時、R010／R011 生育、R013／R014 孩子、R052A 年齡條件、
R055 健康自述、G001／G002 兩條綠燈）加 8 條禁止規則。

**引擎的兩條硬規定**：

- `requires` 缺任何一個欄位就整條跳過，並把那個題組記為「資料不足」——
  這樣才不會把「沒填」誤讀成「填了否定的值」。
- `outcome='never'` 是禁止規則，見下。

**禁止規則 R047–R054 做成會擋下寫入的檢查**，不是註解裡的約定。而且**禁止清單是從
`outcome='never'` 那幾條規則推導出來的**，所以新增一條禁止規則就自動生效——R047「MBTI
不產生黃燈」因此是會 load-bearing 的資料。三層防線：

1. `screening_rules` 上的 trigger，寫入引用禁止欄位的規則直接拒絕
2. `run_screening()` 每次執行前再掃一次整張表（萬一有人把 trigger 停掉，寧可整個不跑）
3. `screening_subject()` 白名單——引擎讀不到完整病歷卡，學歷、收入、身高、體重、MBTI、
   健康告知內容**根本不在它拿得到的 jsonb 裡**。健康只交出「有沒有」與「本人選的揭露時機」。

**初診不會變成繞過遮罩的後門**。`get_screening_for()` 數量永遠給，細節只給
`min_stage <= 目前揭露層級` 的那幾筆，其餘只計入 `hidden`。第 0 層看得到「🔴 1 項」，
但不會知道那一項是生育規劃——第 0 層連精確年齡都看不到。R055 的 `min_stage` 還會**跟著本人
自選的 `health_when` 走**：選「永遠不公開」時，連「有這件事」都不會透露。

過程中抓到一個我自己寫出來的洩漏：`get_visible_match_profiles()` 是用
`to_jsonb(p) - array[...]` 做遮罩的**黑名單**制，所以任何新加的欄位預設都是公開的。
`weekly_work_hours` 是第 2 層資料卻在第 0 層讀得到，`dealbreakers` 同理。兩個都補上了
（`dealbreakers` 完全不外流，只給 `dealbreaker_count`），並加了會擋下回歸的測試。

還有一個排序的坑：欄位必須宣告在第 1 節，不能放在第 13 節。`get_visible_match_profiles()`
在第 2 節就會引用它，而 SQL 函式在**建立當下**就驗證函式本體——欄位還沒存在就直接建立失敗。
（這跟上一輪 `match_user_blocks` 必須排在遮罩函式前面是同一個坑。）

驗證：`tests/pgtest-screening.sql` 在真的 Postgres 16 上跑 **63 項**，從空的 schema 重建後
全綠——含「工時 45 小時不亮任何燈」「四條工時規則區間互斥」「雙方都『不確定』不算一致不亮綠燈」
「學歷／收入／身高／體重／MBTI 從天差地遠改成完全相同，燈號數量一模一樣」「初診結果裡完全
沒有健康告知的內容」「寫入引用收入的規則被擋下來」「被對方封鎖後初診一併查不到」。
前端另加 `smoketest-screening.js` **38 項**，連同既有七份共 **187 項**，全部通過。

### 29. 申請者 CRM 的資料層（規格第 3 步）：病例時間軸與看板欄位

規格見 [`docs/screening-crm-spec.md`](docs/screening-crm-spec.md) 第 4 節。跟規則引擎互不相依。

**四個欄位就夠**：`opened_at`、`last_activity_at`、`closed_reason`、`crm_tags`。
看板九格裡有七格完全從現有欄位算得出來，所以不新增任何狀態欄位——多存一份就多一份不同步的風險。

**事件用資料庫 trigger 記，不是在 RPC 裡補寫。** 規格原本寫要在九支 RPC 裡各加一行，
實作時發現**婉拒根本不走 RPC**——它是前端直接對 `applications` 下 `update`。靠 RPC 補寫會
整條漏掉婉拒，而婉拒正是漏斗上最需要記錄的一步。改成 trigger 之後，連「有人繞過前端直接改
資料」都記得到，稽核價值才成立。前端也**沒有 `application_events` 的 insert 權限**，
唯一的寫入路徑是 SECURITY DEFINER 的 trigger。

**時間軸有可見性分層**：`both`（雙方都看得到的申請進度）／`recipient`（志工筆記、AI 分析）／
`admin`（安全事件，被記錄的人不會知道）。收件匣底下一個「🕐 病例時間軸」，**展開才載入**
——收件匣可能有上百封，不該一進來就打上百次查詢。

**`closed_reason` 自動填、而且只存申請人本來就知道的事。** 規格說要用 RLS 擋掉，但 Postgres
沒有欄位級 RLS，而且 `declined_stage1` 其實沒有洩漏任何新資訊（申請人本來就看得到自己的
`stage` 和 `status`）。所以改成前端寫不進去（進 guard trigger 的還原清單）、由 trigger 依
狀態變化自動填；封鎖與安全事件**絕對不可以**寫進來，一律走 `visibility='admin'` 的事件。

測試抓到兩個實作 bug：

- **`last_activity_at` 只在 UPDATE 時維護**，所以新申請是 null，而「逾期」的查詢是
  `last_activity_at < now() - 7 天` —— null 永遠不會命中。也就是**最該被看到的那種申請
  （送出後三週沒人理）反而不會出現在逾期格**。改成 INSERT 也設。
- **RLS 寫好了但沒 GRANT**，結果 `permission denied for table`，連自己那幾列都讀不到。
  RLS 決定「哪些列」，GRANT 決定「能不能碰這張表」，兩個都要給。

另外聊天訊息**不進時間軸**（會把病例洗版），但會更新 `last_activity_at` ——
否則聊得正熱烈的申請會被算成「逾期未處理」。

驗證：`tests/pgtest-crm.sql` 在真的 Postgres 16 上 **37 項**，含「婉拒是前端直接 update，
trigger 仍然記到了」「前端叫不動 `log_application_event`」「申請人讀不到 recipient-only
的事件」「無關的第三人什麼都看不到」「`exchanged` 只會發生一次」。
前端 `smoketest-crm.js` **23 項**。連同既有兩份 SQL 共 **100 項**、八份瀏覽器測試共
**210 項**，全部通過。

### 30. 認養看板與《認養申請病例》（規格第 4 步）

> 不要再讓志工看到「124 封申請」，而是看到「124 個病例目前分別在哪一站」。

**收件匣直接改成看板，不是另開一個分頁。** 兩個地方做同一件事正是這次要避免的事。
舊的收件匣（把每一封的完整回答攤平在同一頁）變成點進去之後的《認養申請病例》，
上層是候診名單。

**九個分格**：📨 新申請／🩺 待初診／📋 第一階段待審／💬 第二階段／👀 日常觀察／
❤️ 等待雙向解鎖／🌱 完成認養手續／💤 逾期／🏠 已婉拒結案。
**分格刻意會重疊**——一筆送出三週沒人理的新申請同時屬於 📨 與 💤。分格是鏡頭，
不是互斥的抽屜；志工要問的是「有沒有卡住的」，不是「這封該歸在哪一格」。

**五個快篩**（可疊加）：只看有紅燈／只看超過 7 天沒處理／只看優先邀請／只看未讀訊息／
只看需要補件。「需要補件」定義為初診有 ⚪（資料不足）——不是對方偷懶，是有欄位沒填到
所以判斷不出來，這種最適合用一封罐頭去問。

**整個看板只打一次 RPC。** 初診燈號在 `screening_results`，那張表刻意不開放給前端直接查
（直接查得到就等於繞過 `min_stage` 分層），所以一封一封問的話 124 封就是 124 次往返。
`get_crm_board()` 一次把燈號、未讀數、擱置天數全算好；**九格與五個快篩純粹是前端分類，
切換不會再打伺服器**。看板只帶數量，細節仍然只能走 `get_screening_for()`。

**列上的狀態寫「卡在誰身上」**，不是「走到第幾階段」——第三階段本身不是待辦事項，
所以寫的是「等你同意解鎖」「等對方作答」「第一階段待審」。

**《認養申請病例》七區塊**：📋 病例摘要（含標籤編輯）／🩺 初診結果／📝 申請問卷與處理／
💬 面談紀錄（志工備註）／📨 回覆建議／🚨 安全與檢舉紀錄／🕐 病例時間軸。

- ⑤ 回覆建議把規格第 7 步往前拉了一小段：`template_master` 加了 `reason_codes`，
  seed 了五封對得上目前規則理由碼的罐頭。推薦是陣列交集，**不用 AI、不扣點數**。
  按「帶入下一則回覆」之後，婉拒／通過時的輸入框就會預先填好那封。
- ⑥ 只顯示**你自己**送出過的檢舉與封鎖狀態。別人的檢舉屬於管理員的處理範圍——
  讓收件方看得到等於洩漏其他會員的行為。

**`opened_at` 的語意這一步才真正成立**：第 3 步時收件匣把所有回答攤開，「畫出來」就等於
「看過了」；現在改成點進病例才標記，「📨 新申請」這一格才有意義。

實作時抓到一個 bug：病例裡的時間軸預設是展開的，而 `ontoggle` **只在狀態改變時觸發**——
所以一開始就展開的那個永遠不會載入，會一直停在空的。要另外主動載入一次。

驗證：`tests/pgtest-board.sql` 在真的 Postgres 16 上 **34 項**（含「看板只帶燈號數量、
不帶初診細節文案」「申請人自己的看板是空的」「別人的病例打不開」「別人送出的檢舉不會出現」）。

### 31. 罐頭中心：理由碼對應改成管理後台可編輯（規格第 7 步）

「黃燈 → 理由碼 → 罐頭」這條鏈上最容易壞掉的地方是**理由碼打錯字**：打錯的罐頭永遠不會
被推薦，而且畫面上完全看不出來——不會有人發現。所以後台的理由碼**一律用勾的**，
勾選清單直接來自規則庫本身（`list_reason_codes()`），每個理由碼旁邊還寫出是哪幾條規則
會亮，不然沒人知道自己在勾什麼。

**兩種缺口直接寫在最上面**，不用自己比對：

- ⚠️ **有理由碼但沒有任何罐頭** → 初診亮到那盞燈時，收件方拿不到任何回覆建議
- ⚠️ **罐頭指向不存在的理由碼** → 這封永遠不會被推薦（通常是規則改過了），
  下面會標成「已失效」，取消勾選就好

勾選當下就重算覆蓋率，不用等按儲存——不然改到一半看不出還缺什麼。

**修掉一個從第 10 節就存在、而且一直沒被發現的 bug**：`template_master` 有 RLS policy
但**沒有任何 GRANT**，所以 `authenticated` 連這張表都碰不到。前端的 `getTemplateMaster()`
被 `try/catch` 包著，於是「範本主檔管理」一直是靜靜的空白——**這個功能從來沒有運作過**，
連帶會員「我的回覆範本」的預設值也一直是空的。這跟第 29 節 `application_events` 是同一個坑：
RLS 決定「哪些列」，GRANT 決定「能不能碰這張表」，兩個都要給。

**已知限制**：後台只能編輯既有的罐頭，不能新增或刪除。所以覆蓋率缺口目前只能靠「把既有的
罐頭掛到那個理由碼上」來補，沒辦法從畫面上寫一封全新的。

驗證：`tests/pgtest-templates.sql` **14 項**（含「一般會員讀得到範本主檔」——就是上面那個
GRANT、「一般會員改不動理由碼」「改完之後推薦真的跟著變」「指向不存在理由碼的罐頭抓得出來」）。
前端 `smoketest-templates.js` **28 項**（含「完全沒有讓人自由輸入理由碼的欄位」
「失效的理由碼標成已失效而且是勾著的」「沒勾任何理由碼的送出空陣列而不是 undefined」）。
連同既有測試共 SQL **148 項**、瀏覽器 **300 項**，全部通過。

### 32. 規則庫補完：Dealbreaker 表單、其餘 41 條規則、安全規則進管理後台（規格第 5、6、8 步）

**🔴 的通則寫死在規則裡：雙方都標成「不可妥協」才成立。** 單方堅持只會是 🟡「值得問」——
那是當事人自己要判斷的事，系統不會替他判定不適合。「🟡／🔴 依重要性」用 `escalate` 表達

**R056–R058 進管理後台**。這三條跟其他 55 條形狀不一樣：它們是「關於某一個人」，不是

### 33. 第二階段結構化問診 S2-01～S2-05：規則先進庫

六條規則已經進庫（S2-04 拆成「節奏不同」與「會不會說一聲」兩條）。這一輪先掛著

**重要度改成四級**：⚪ 不在意／🟡 可以討論／🟠 非常重要／🔴 不可妥協。
但 **🟠 不會讓燈變紅** —— 🔴 的判定維持「雙方都不可妥協」，🟠 只讓同一盞黃燈排得比較前面。
不然「非常重要」會變成第二個不可妥協，紅燈就浮濫了。

跟需求規格的三處出入，都是為了不製造重複：

  都在讀它，再開五個欄位等於同一件事有兩個來源。改成重要度仍存 `dealbreakers`，
  只是**問的地方**搬到第二階段題目旁邊。
- **四題不新增欄位**：`contact_frequency`／`alone_time_need`／`parents_in_decisions`／

  同一個問題問兩次。改成把選項換成規格裡更細的那一版，舊值有一對一的資料遷移。
  真正新增的只有五個欄位。
- **S2 規則的 topic 刻意跟簡易版相同、priority 刻意比簡易版小**，
  翻開開關後「一個題組只留一條」會自動留下比較細的那一條。

文案上守住的幾件事（都有測試盯著）：S2-02 主動否定「一個太黏、一個太冷淡」；
S2-05 寫成「界線設定不同」而不是判誰媽寶；**S2-04B 明講「這不等於冷暴力」**，
輸出是 ⚪ 而不是黃燈或紅燈 —— 真正是否涉及懲罰性沉默要看實際情境，系統不替任何人下判斷。

**測試抓到三個 bug**，其中一個影響已經上線的規則：

- **S2 的 priority 一開始比簡易版大**，結果「只留一條」留下的是比較粗的那一條，等於白做。

驗證：`tests/pgtest-stage2.sql` **30 項**（含「每一條都命中」「一方只標 🟠 不會亮 🔴」

### 34. 第二階段結構化表單，以及把 62% 那個數字從系統裡拿掉

**（一）結構化表單只有五題。** 48 題不會全部結構化——只有真的會餵給規則引擎的題目才需要，
其餘保留自由回答，不然認養面談會變成一份超長的人格測驗。所以表單就是 S2-01～S2-05
這五題、九個答案欄，加五個「這件事對你有多重要」，排在第二階段自由回答的前面。

- 答案**存回個人資料卡**（分階段揭露照舊），不是存在這一份申請上——那是關於你這個人的事實，
  不是關於這一次配對的回答。已經答過的會預填，不用重答。
- 重要度一樣寫進既有的 `dealbreakers`，而且**只更新這五個 topic**：先前設過、不屬於這五題的
  重要度不會被洗掉；選「不在意」則是把那個 key 刪掉，而不是留一個 `none`
  （留著會被當成「設定過」）。沒選的答案欄**不送出空字串**，不然會把先前答過的洗掉。
- 送出順序是**先存結構化、再送自由回答**。反過來的話自由回答一送出表單就重畫，選單就讀不到了。
- schema §21 把六條 S2 規則打開。

**（二）`vet_scores` 與「匹配度 62%」整個移除。** 付費 AI 從「給一個分數」改成
「讀一份初診報告，補規則看不到的部分」：

### 35. 八個生活場景：一份共同的資料來源，以及最後五條規則怎麼開

原則不變：**不是為了湊滿題數而問問題，只有會改變初診結果、AI 問診方向或審核流程的
資料才值得結構化。** 所以最後那五條 `enabled=false` 的規則不是直接打開——
舊條件式讀的是 `guests_at_home`、`housework_split`、`req_conversion`、`ex_contact_freq`
這些**從來沒有問過**的欄位，直接開只會得到一條永遠不命中的規則。

先決定「問什麼才問得到真話」，再把規則重寫到那些欄位上：

| 原規則 | 怎麼處理 | 為什麼 |
|---|---|---|
| R034 居家社交 | 重寫並開啟（＋R034B 🔴） | 問的不是外向／內向，是共同生活時私人空間的界線 |
| R035 家務 | 重寫並開啟（＋R035B 整潔標準） | 問「你願不願意做家事」沒有辨識力，人人都選平均分攤；改問「你對公平的定義」 |
| R036 性別分工 | **不獨立成題**，改成 R035 的子規則 | 單獨問會變成立場問卷，社會期許會讓答案失真 |
| R041 宗教 | 重寫並開啟（＋R041B 子女教育、R041C ⚪） | 不問信仰內容，只問要求與界線 |
| R044 前任／異性 | 重寫並開啟（＋R044B、R044C 複選清單） | 不問「你能不能接受前任」，問「哪些行為需要先講一聲」 |

跟原始規劃的一處出入：**R035 的前兩題已經存在了**。`housework_model` 與
`cleanliness_conflict_style` 是上一輪 S2-03 就在用的欄位，選項字串幾乎逐字相同。
照規劃新增 `cleanliness_negotiation` 會讓同一個問題有兩個欄位、兩個來源，
所以只新增 `housework_fairness` 一個欄位，前兩題沿用。

三條規則的分寸（都有測試盯著）：

- **信仰不同永遠不亮燈**，資料庫裡也沒有「信仰是什麼」這個欄位。會亮的只有
  「要求對方改變信仰」與「子女教育的期待落差」。R041C 是 ⚪ 中性提示而不是黃燈，
  文案明說「這不是問題」——信仰虔誠不是需要處理的事。
- **有異性朋友永遠不亮燈。** 會亮的是兩個人對界線的定義差太多。
- **R036 不點名任何性別**，只說兩邊的前提不一樣，並明講系統不判斷哪一種比較好。

**一份共同的資料來源。** `data/relationship-topics.json` 是八個場景的唯一來源，
第二階段問卷、初診規則庫與 AI 診療室都讀它：

```
data/relationship-topics.json     ← 唯一的來源，手改這一份
  ├─ js/relationship-topics.js    ← 產生物，index.html／dashboard.html 用
  └─ data/topic-options.sql       ← 產生物，pgtest-topics.sql 用
node tools/gen-topics.mjs         # 重新產生
node tools/gen-topics.mjs --check # 檢查有沒有漂移
```

為什麼不讓網頁直接 `fetch` 那份 JSON：暖陽是純靜態站，測試用 `file://` 開，
`fetch` 會被 CORS 擋掉。產生一支 `<script src>` 就能載入的 `.js`，兩個頁面都用得到，
也不需要任何 build server。

**這一輪抓到四個坑，其中兩個是「安靜地失效」型的：**

- **`screening_subject()` 是白名單。** 新欄位沒加進去，規則讀到的永遠是 null——
  規則不會報錯、不會亮紅字，只是那個題組從此不會亮燈。這跟遮罩黑名單漏一個是
  同一個坑的反面，現在兩邊都由測試逐欄盯著。
- **`jsonb_build_object` 最多 100 個參數。** 第 9 個新欄位正好把遮罩函式頂爆，
  整份 schema 載不進去。拆成兩組 `||` 串起來。
- **靜態讀 SQL 檔比對規則字串會誤報。** schema 是可重跑的檔案，同一條規則會先在
  第 18 節建立、再被第 20／23 節改寫，讀檔看到的是所有歷史版本而不是最終狀態。
  那項檢查移到真的 Postgres 上跑（`pgtest-topics.sql`）——一支會誤報的檢查，
  下場就是大家開始忽略它。
- **`req_family_involvement` 不該進遮罩黑名單。** 它跟 `req_marital`／`req_kids`
  同一類，是「希望對方」的條件，本來就是寫給別人看的。所以檢查改成
  **每個欄位都必須有一個明確的揭露決定**：要嘛在黑名單裡，要嘛在 JSON 裡標
  `public:true` 並寫出理由。沒有第三種選項——忘了想就會被擋下來。

驗證：`tests/pgtest-topics.sql` **45 項**（含「規則比對的每一個字串都是選項裡真的有的字」
「每個結構化欄位都至少有一條啟用中的規則在讀，不然不該問」「資料庫裡沒有信仰是什麼這個欄位」）。
連同既有測試共 SQL **264 項**、瀏覽器 **417 項**，全部通過。

**還沒做**：規則庫已經沒有停用中的規則了。下一輪要加的是第 59 條以後的新規則，
或是把八個場景的答案接進 CRM 的快篩。

### 36. 忘記密碼、Email 驗證提示、檢舉時效倒數

三個「文件說有、畫面上沒有」的缺口。共同點是：**都不會報錯，只會讓人卡住而不知道為什麼**。

**忘記密碼**：登入視窗多一個模式。切過去時只留 Email 欄（密碼欄留著會讓人不確定該填哪一個），
Google 按鈕也收起來（Google 帳號沒有密碼可以重設）。
送出後不論那個 Email 有沒有註冊過都回同一句話——回報「查無此帳號」等於送給任何人
一支「這個信箱有沒有在這個站註冊」的查詢工具。

使用者點了信裡的連結回站上，Supabase 會丟一個 `PASSWORD_RECOVERY` 事件。
這時候**不直接放行進站**，而是打開「設定新密碼」——那是一個 recovery session，
它存在的唯一目的就是讓人改密碼。

> 重設信的連結會回到 `window.location.origin + pathname`，所以那個網址
> **必須在 Supabase 的 Redirect URLs 白名單裡**（第 2 步設過了）。
> 不在白名單的話使用者會被丟回 Site URL，看起來像是連結壞掉。

**Email 驗證提示**：專案如果開了 Confirm email，沒驗證的帳號有些操作會被擋，
但預設畫面上完全沒有說明，使用者只會看到操作失敗。現在會出現一條橫幅，
寫出是哪個信箱、提醒去看垃圾郵件匣，並給一顆重寄按鈕。
專案沒開驗證的話 `email_confirmed_at` 一開始就有值，橫幅不會出現。

**檢舉時效**：條款與安全中心都寫著「3 個工作日內回覆」。承諾寫在條款裡、卻要靠人記得去
後台看，那個承諾遲早會跳票，而且跳票的時候沒有人會發現。現在管理後台會：
算出已經過了幾個工作日（六日不算）、標出逾期幾件、把**等最久的排在最前面**
（待處理清單的正確順序是「誰等最久」，不是「誰最新」）。
那一行也誠實寫著「目前沒有排程或 email 通知在盯這個時效」——
它讓時效看得見，但它不是通知。

驗證：`smoketest-auth-sla.js` **37 項**（含「不透露帳號存不存在」「太短的新密碼不會送出」
「一週前＝5 個工作日、兩週前＝10 個」「壞掉的時間字串不會讓整頁爆掉」）。
工作日的斷言刻意不寫死日期——任何連續 7 個日曆天一定正好含 5 個工作日，
所以不管哪一天跑答案都一樣。

### 37. 對話室的三級安全提醒與 Consent Mode

第二階段對話室升級成「暖陽問診對話室」的第一步：安全那一層。
偵測在伺服器端跑（`send_match_message` 裡），等級存在訊息上——放前端的話，
改一下 devtools 就沒有了。

**兩條寫死的原則，違反哪一條都比漏偵測更糟：**

**（一）系統不做法律定性。** 不寫「此言論構成性騷擾」。是否構成性騷擾、適用哪一套法律、
有沒有刑事責任，都要看情境、關係、是否持續、是否違反意願等具體事實判斷，
不能只靠一句文字讓系統下法律結論。文案一律是「這段內容**可能涉及**什麼」，
並把選項交回當事人。測試會擋下任何出現「構成／觸犯／刑法／違法」字樣的文案。

**（二）不能只做關鍵字比對。** 這是整個功能最容易做壞的地方：

> 「我不喜歡別人問我會不會口交」跟「妳會口交嗎」含同一個詞。
> 看到關鍵字就亮紅燈，會讓人不敢談論自己的界線——**剛好害到最需要保護的那個人。**

所以偵測是兩層：先抓訊號**類別**（露骨性內容／身體話題／威脅／強迫／私密影像／
第二人稱要求／在講自己的界線／表達拒絕），再看訊號的**組合**。
「在講自己的界線」與「在引述別人的話」是反向訊號，命中就不亮燈。

三個等級：

| 等級 | 條件 | 例 |
|---|---|---|
| 🟡 界線提醒 | 身體話題 ＋ 對對方提出要求 | 「可以看看妳身材嗎」 |
| 🟠 性話題警示 | 露骨性內容 ＋ 對對方提出要求 | 「妳會口交嗎」 |
| 🔴 安全提醒 | 人身威脅；或威脅／強迫 ＋ 性內容；或**對方說過不要之後再問一次** | 「不給我看我就把妳的裸照傳出去」 |

同一句「妳會口交嗎」，第一次問是 🟠，在對方說過「請停下」之後再送一次就是 🔴——
同樣的字，性質已經不一樣了。

**訊息不會被擋下來。** 擋掉的話，送出的人只會改幾個字再送一次，
而收到的人反而失去「這個人剛剛說了什麼」的證據。
暖陽的選擇是讓它送出去、標記起來、把選項交給收到的人：
［我覺得不舒服］［封鎖］［檢舉］。第一顆只是把話填進輸入框，不會替使用者送出任何東西——
很多時候需要的只是把界線講出來，而不是立刻把事情鬧大。

**Consent Mode**：兩個成年人真的想談性話題時，不該一看到性詞就一直跳警告。
但它是兩個人**各自**按下才成立，隨時可以撤回，而且 RPC 只動 `auth.uid()` 自己那一列——
替對方按下同意是最不能允許的事。

> 即使雙方同意，**威脅、強迫、散布私密影像，以及在對方表示停止之後仍持續，
> 仍然會亮 🔴**。同意談性話題，從來不等於同意被威脅。
> 這一條在畫面上一開始就寫出來，不是藏在小字裡。

驗證：`tests/pgtest-chatsafety.sql` **42 項**、`smoketest-chat-safety.js` **31 項**。
SQL 那一份最重要的不是「有沒有抓到」，而是**有沒有抓錯**——
六條誤判防線排在整份測試的最前面。
連同既有測試共 SQL **306 項**、瀏覽器 **501 項**，全部通過。

**尚未實作、已寫成規格**：交換聯絡方式之後的 🌱 暖陽陪伴紀錄
（回憶、里程碑、共同目標、關係健康檢查、衝突診療、回憶膠囊、年度回顧）。
見 `docs/companion-journal-spec.md`——六張新表、一套 AI 讀取權限模型，
以及五個需要先決定的分岔點（其中「關係結束後紀錄怎麼辦」必須在動工前想清楚）。

### 38. 貼上自己寫過的自介，讓主治醫師幫忙預填

登記精靈第一步多一顆「貼上我寫過的自介」。已經在 Dcard 徵友文或交友軟體寫過一次的人，
不必為了暖陽再重寫一遍。三條規則寫死在程式裡：

**（一）只處理使用者自己寫的文章。** 送出前要本人明確勾選「這是我自己寫的」，
prompt 也明講「文章裡如果提到別人（前任、朋友、家人），那些是別人的資料，不要抽出來」。
這個功能不是拿來把別人的徵友文建檔——那是把第三方的個人資料未經同意搬進交友站。

**（二）合法選項一律從畫面上的 `<select>` 現讀，不在程式裡抄第二份。**
抄一份就會有第二份會走鐘的東西，而且走鐘的方式最難發現：AI 回了一個不在選項裡的值，
硬塞進 `<select>` 只會變成一個看不出來的空值——**比沒填還糟**。
所以不在選項裡的值就地丟掉，並且**把丟掉的東西列給使用者看**
（「學歷：博士後研究，已略過」），而不是安靜地少一欄。多選則是逐項判斷，
合法的留下、不合法的丟掉，不會因為一項不合法就整組放棄。

**（三）只填進表單，不直接存檔。** 每一欄都可以逐項取消，套用之後仍然要自己按
「儲存登記」。AI 讀錯一個欄位很正常，讀錯而且自動存起來就不正常了。

**你自己的**健康告知、負債與收入不在可匯入的欄位裡：那幾項有各自的分階段揭露設定，
讀錯的代價比其他欄位高很多。（「對伴侶負債的接受度」是你對別人的條件、不是你的財務狀況，
跟 `req_kids`／`req_marital` 同一類，可以匯入。）

驗證：`smoketest-import.js` **30 項**。AI 的回應刻意做得很難搞——
一個不在選項裡的學歷、一個一半合法一半不合法的多選、一個不存在的欄位、一個空字串。
連同既有測試共 SQL **306 項**、瀏覽器 **531 項**，全部通過。

**AI 獸人形象生成圖**：「自行上傳（需審核）」那一半現有的照片審核系統已經涵蓋
（登記時要選本人照片或 AI 形象照，AI 形象照必須聲明與本人高度相似並經人工核對）。
「生成」那一半還沒做，因為它需要一個**影像**生成服務——
這個 repo 目前唯一的 AI 代理是文字的（Claude 不生圖），要接得先決定用哪一家。

### 39. 意見回饋

個人中心多一個「意見回饋」子分頁，管理後台多一區。壞掉的地方、看不懂的說明、
想要的功能都可以寫。

**跟檢舉刻意分開，而且分得很用力。** 不是為了整齊——混在一起最糟的後果不是雜亂，
是**一則「有人一直傳很噁心的訊息給我」掉進一個沒有時效、沒有人每天看的產品意見清單裡**。
所以：

- 表單一開始就寫「如果是關於某個人的行為，請改用檢舉」，並說明差在哪
  （檢舉會排進人工安全審查，這裡不會）。
- 送出前就地檢查文字，看起來像在描述某個人的行為時**先問一次**。
- 但**問完仍然送得出去**。使用者說「這件事我就是想當成產品問題講」也是他的權利，
  提醒不是攔截。

那個檢查沿用第 24 節對話室的訊號類別，不另外抄一份詞庫——抄一份就會有第二份會走鐘的東西。
過程中這一點抓到兩個 bug：

- 第一版只比對訊號**類別**，結果「我不喜歡別人問我會不會口交，希望站上能講清楚界線」
  也被判成在講某個人。那正是第 24 節的反向訊號要擋掉的誤判，**只抄一半等於把防線丟掉**。
  改成直接用整支 `chat_safety_level()`。
- 但接著發現語境不同：對話室裡威脅是第二人稱（「讓**妳**好看」），
  意見回饋裡是本人轉述（「他說要讓**我**好看」）。所以多一個 `reported` 訊號類別，
  **只有意見回饋在用**——在對話室裡命中的會是受害者自己那則訊息，
  替受害者的訊息標紅燈是最糟的結果。

**不承諾做不到的回覆。** 寫的是「我們會看每一則，但不保證每一則都會回覆」，
需要一定要有回覆的事情指向真的信箱。檢舉那個「3 個工作日」目前已經沒有排程在盯了
（見第 36 節），不該再多一個做不到的承諾。

**瀏覽器資訊預設不附。** 版面跑版的回報沒有這個幾乎修不了，但那是使用者的資訊。
勾之前就看得到會送出什麼，而且只有瀏覽器家族、作業系統與畫面寬度——
不是完整 UA、沒有任何識別碼。送出後勾選會復原，不會變成一個隱形的長期同意。

**送出去不能是黑洞。** 使用者在同一頁看得到自己送過的每一則、目前的狀態，
以及站方寫的回覆——不然沒有人會想送第二次。

### 40. 修掉一個只在「既有資料庫」上才會出現的錯

實際回報：把整份 `supabase-schema.sql` 重貼到正在跑的 Supabase 專案上，炸出

```
ERROR: 23514: new row for relation "chat_safety_signals"
violates check constraint "chat_safety_signals_class_check"
DETAIL: Failing row contains (P_TOME, reported, ...)
```

**原因：`create table if not exists` 對已經存在的表是完全的 no-op。**
`chat_safety_signals` 在第 24 節就建好了，第 25 節才把 `'reported'` 加進 `class`
的清單裡——但那個新的 `check` 只寫在 `create table` 裡面，所以在既有資料庫上
**永遠不會生效**。而且它不會在載入 schema 時就報錯，是等到那一行 `insert` 才炸。

**為什麼測試沒抓到：所有 SQL 測試都是先 `drop schema` 再載入**，
也就是每一次都在全新的資料庫上跑——那剛好是唯一碰不到這個問題的跑法。
測試覆蓋率再高，跑錯路徑一樣看不到。

修法有兩層：

1. **凡是「之後可能會加值」的 `check`，一律拉出來寫成獨立的
   `alter table drop constraint if exists` ＋ `add constraint`**，重跑才會更新。
   已經改掉 `chat_safety_signals.class`、`match_messages.safety_level`、
   `feedback.category`、`feedback.status`。
   （`reports.category` 本來就是這樣寫的，這次是照那個既有的正確寫法補齊。）
2. **新增 `tests/pgtest-upgrade.sql`**：把資料庫改回舊版的樣子（換上舊的 check、
   刪掉新資料），然後 `\i supabase-schema.sql` 重貼一次，再確認舊約束真的被換掉了。
   README 一直寫著「重新貼一次整份 `supabase-schema.sql` 執行即可」，
   這一份就是去驗那句話是不是真的——**在此之前沒有任何東西在驗它**。

> 這一份測試要**從 repo 根目錄跑**，因為它會 `\i supabase-schema.sql`。

驗證：`tests/pgtest-upgrade.sql` **6 項**。
連同既有測試共 SQL **339 項**、瀏覽器 **562 項**，全部通過。

### 41. 興趣、個性、物種、性別都可以自己新增

內建選項留著，旁邊多一個「自己新增」。物種與性別的下拉多一個「＋ 其他（自己填）」。

**做這個之前先確認了一件事，而它決定了整個做法：這四個欄位在佈告欄上是第 0 層公開的。**

也就是說，開放自由輸入等於開了一條「把任何文字放到所有人都看得到的地方」的管道——
而暖陽整套四層漸進式揭露，就是為了讓聯絡方式要走完三階段、雙方都同意才交換。
一個叫「我的興趣」的欄位如果可以填「IG: xxx_1234」，**整套解鎖流程就被繞過去了，
而且是使用者自己繞的，不會有人來檢舉。**

所以自訂值一律在伺服器端檢查（schema 第 26 節），前端那一層只是讓人早一點知道：

- email、手機、LINE ID、IG／FB／Telegram 帳號、`@帳號`、網址 → 擋下來並說明該填在哪一欄
- 標籤上限 12 個字、20 個
- 物種與性別的自訂值一樣檢查，一樣限制長度

檢查的是**形式**（長度、數量、有沒有聯絡方式），不是內容好壞——系統不評價別人怎麼描述自己。

**兩個實作上的判斷：**

- **凡是使用者會發現不見的東西，都要報錯講清楚。** 第一版把清洗排在檢查前面，
  結果「IG @mycoolname」因為超過 12 個字先被長度過濾掉，聯絡方式的檢查根本沒跑到——
  使用者以為存好了，實際上那一項消失了，而且他不知道為什麼。
  改成**先檢查原始輸入、最後才清洗**；清洗只負責他不會發現的整理（修剪空白、去重複）。
- **`__other__` 是哨兵值，不是答案。** 讀值一律走 `pickOrOther()`，
  呼叫端不用記得判斷——忘記判斷的話，存進資料庫的會是字串 `"__other__"`，
  而且畫面上看起來像一個正常的值。匯入功能的合法選項也把它濾掉了。

**顯示端**：`speciesLabel()` / `genderLabel()` 查不到對照表就直接用原文，
不會掉成空白或「未知」；自訂物種給一個通用的 🐾。
自訂性別的代稱一律用**「他們」**——猜錯的代價比不猜高，而且對方本來就選擇了不套用既有分類。

**佈告欄的物種篩選只列內建的**：自訂物種每個人寫法都不一樣，放進篩選只會變成
一長串幾乎沒有人會選的選項。

另外有一支 `popular_custom_tags()`，讓「已經有幾個人在用」的自訂標籤可以推薦給後來的人，
省得每個人各自打一次「攝影」。**門檻至少 3 個人**——只有一個人在用的標籤如果被端出來，
那等於用一個標籤反向指認一個人。

驗證：`tests/pgtest-customtags.sql` **39 項**（含「一般標籤不會被誤擋」六條、
「太長的標籤會報錯而不是靜靜消失」「很長的聯絡方式也擋得住」
「被擋下來的那次更新整筆都沒生效」）與 `smoketest-customtags.js` **38 項**。
連同既有測試共 SQL **378 項**、瀏覽器 **600 項**，全部通過。

### 42. 🌱 暖陽陪伴紀錄（規格第 1、2 步）：companion_links 與對話書籤

`docs/companion-journal-spec.md` 排的順序是「第 1 步關係本身、第 2 步聊天與紀錄之間那座橋」，
這一輪就做這兩步。

**先寫死三條產品規則，而且是寫在 schema 第 27 節的註解裡，不是寫在文件某一頁：**

1. **不建立陪伴紀錄也能解鎖聯絡方式。** 配對功能在第三階段就完成了。
   一旦哪個地方把它寫成條件，陪伴紀錄就從「值得回來的理由」變成「不做就拿不到東西的關卡」。
2. **使用者離開不算失敗。** 兩個人交換聯絡方式之後再也沒登入，可能代表暖陽已經完成它的工作。
   所以這裡沒有連續登入、沒有簽到、沒有「你已經 N 天沒有記錄了」。
3. **不打分數。** 不存任何關係評分，之後也不會加。

規則 1 與 2 都有測試在守：SQL 那邊檢查四個解鎖函式的定義裡完全沒有出現 `companion`，
也檢查 `companion_links` 沒有任何 score／streak／level 欄位；瀏覽器那邊檢查
還不到第三階段時陪伴紀錄整塊**不在 DOM 裡**——先給看再說「你還不能用」，就是把它變成關卡。

**規格第 7.1 節那個沒有答案的分岔（單方面可不可以建立）**，這一輪的解法是拆成兩件事：

- **共同的那本**（`companion_links`）要兩個人各自按下才成立，跟 Consent Mode 同一個模式。
  一本關於兩個人的紀錄不該由一個人替兩個人決定；而且未經邀請的
  「某某想跟你建立陪伴紀錄」本身就是一種壓力。
- **書籤是個人的，預設只有自己看得到。** 想留一句話不需要對方批准，也不會通知對方。
  要分享再自己改成共同。

這樣就同時有了「回憶是自己的」與「共同的東西要雙方同意」。

**🔖 記住這句**：對話裡每一則訊息都可以收藏，四種——
💛 喜歡的話／🌱 關係里程碑／📝 重要約定／🎁 想保存的回憶。
同一種再按一次是取消，換一種是改類型，一顆按鈕就夠。
**共同分享的是那個標記，不是那段心情**：改成共同之後對方看得到你記住了這句話，
但看不到你在備註裡寫了什麼。

**兩個實作上的判斷：**

- **暫停之後回來不重算起算日。** 第一版寫成「只要不是 active 就重設 `started_at`」，
  結果暫停一次再回來，「你們的陪伴紀錄從 X 開始」就被洗掉了——那等於把暫停講成一次失敗，
  剛好違反規則 2。改成只在 pending → active 那一次寫入。
- **取消收藏時前端一定要把備註清空送出去。** 伺服器的規則是「同一種＋沒有備註＝取消，
  同一種＋有備註＝補上備註」；前端如果順手把現有備註一起送回去，
  按「取消收藏」會變成儲存。

文案上刻意避開的東西：沒有 ⚠️、沒有紅點、沒有「尚未建立」「完成度」；
被邀請的一方沒有一顆叫「拒絕」的按鈕（不按就是不按，而且對方不會被通知你拒絕了），
等待的一方也沒有任何催促對方的入口。

驗證：`tests/pgtest-companion.sql` **52 項**（含「替對方按下同意是做不到的」
「暫停再回來不會重算起算日」「直接 select 也看不到對方的私人書籤」
「訊息被刪掉時書籤跟著走」）與 `smoketest-companion.js` **74 項**。
連同既有測試共 SQL **430 項**、瀏覽器 **676 項**，全部通過。

### 43. 🌱 陪伴紀錄第 3～8 步：回憶、共同目標、關係健康檢查、診療室、回憶膠囊、結束處置

個人中心多一個 **🌱 陪伴紀錄** 子分頁，六格：時間線／共同目標／關係健康檢查／
診療室／回憶膠囊／這段紀錄。schema 第 28～31 節。

**這個子分頁沒有陪伴紀錄的人看不到。** 不是隱藏功能，是不要讓人看到一個空的、
寫著「你還沒有陪伴紀錄」的分頁——那會把它變成一件沒完成的事。

#### 第 3、4 步：時間線與共同目標

時間線把**回憶、里程碑、對話書籤**三種合在一起照日期排。書籤本來就是第 2 步定義的
「聊天與陪伴紀錄之間的橋」，所以它們是時間線的第一批內容。

- **暫停之後共同的那本唯讀，但自己的筆記還能寫。** 一方撤回同意就繼續往共同的本子寫，
  等於當作沒看到；但把人鎖在自己的筆記外面，那本來就是他自己的。
  畫面上「誰看得到」的下拉會只剩「只有我看得到」。
- **讀得到 ≠ 改得動。** 對方寫的那幾則沒有刪除鈕，伺服器端也擋。
- **里程碑不排順序，共同目標沒有完成率。** 一份共同目標清單長出「完成 3/8」就變成考核表了。
  `status` 一定要有 `paused`（先放著）——只給「未開始／進行中／完成」，
  「這件事我們現在不想推」就只能留在未開始裡看起來像拖延。

#### 第 5 步：關係健康檢查

`share_with_partner` 預設 `false`，而且**那個預設值本身就是規則**。
共同觀察只在兩邊都選擇分享時才產生，而且只列**兩個人答案一樣**的那幾項——
不一樣的地方整題不出現，差異不是一件要被指出來處理的事。

摘要裡沒有分數。選項刻意用文字而不是 1～5：數字放在那裡，遲早會有人把它加起來，
然後就有了一個沒有校準基礎的「關係健康度」。取而代之的是「一個可以談的方向」，
而且寫成問句。

每 30 天最多一次。這個上限的用途是**擋住系統自己**——一旦可以天天填，
畫面上遲早會長出「你已經 5 天沒有回診了」。

#### 第 6、7 步：診療室

規格第 3 節開頭寫著「這是最容易做錯的地方」，所以這一段的每個決定都寫在測試裡：

- 七個授權**預設全部 false**，一次只開一格，取消勾選之後下一次就讀不到。
- **規格原本要求的 `allow_chat_range` 欄位不存在。** 一個叫 `allow_*` 的欄位存在資料庫裡，
  遲早會被當成常設開關讀，而那正好違反規格自己寫的「對話的授權是一次性的」。
  改成 `last_chat_days`，只拿來預填畫面，組 context 時**完全不看它**。
- 由「共同分析要雙方同意」再推出一條規格沒寫、但不補上就會破功的規則：
  **對話只能在 joint 模式、兩人都同意、而且這一次明確指定天數時才進得去。**
  對話裡有對方說的話；solo 模式說好了「只讀使用者自己給的片段」，
  就不能從後門把整段對話撈進去。
- 送出前可以按「先看這一次會送出什麼」，把整包 context 原封不動列出來。

**安全模式**接第 24 節對話室的偵測，兩邊同一組，才不會「對話室亮紅燈、診療室卻繼續勸和」。
另外補了一類 `reported_harm`，處理規格點名的那句
**「他打我，但我不知道是不是我先惹他生氣」**——那句話沒有威脅任何人，
是受害者在轉述發生在自己身上的事，對話室那套（看的是「有人在對另一個人要求或威脅」）抓不到。
跟第 25 節的 `reported` 分開，是為了不要把「他逼我太緊」這種關係壓力也推進安全模式。

命中安全模式時**根本不呼叫 AI**：把這種輸入交給一個關係協調的 prompt，
最好的結果也只是勸和，而「各退一步」會把責任推回受害的一方。

#### 第 8 步（一半）：回憶膠囊與結束處置

- 到期只代表「可以開」。關係非 `active` 時**不自動打開**，只靜靜列一行，點之前先問一次。
  半年後自動跳出來的那封信，如果那時候兩個人已經分開了，它會變成傷害。
- 膠囊對方連「有這封信」都看不到。
- 結束之後兩邊各自選處置（全部刪除／封存唯讀／只留我自己寫的），**選了立刻執行**。
- 一方刪除會在封存本留下「原本有 N 則已被作者刪除」——不留的話另一方會以為自己記錯了。
- **對方選了什麼不揭露。** 那是他自己的決定，知道了也改變不了什麼，
  只會變成分手之後多一件可以拿來想的事。

**排程還是沒有，所以介面上照實說。** `purge_due_companion_links()` 寫好了，
但沒有東西每天呼叫它。畫面上因此**不承諾**「30 天後系統會自動刪除」，
而是寫「目前沒有自動清理在跑：不選的話，東西會留著」。
承諾了卻沒有東西在執行，比不承諾更糟。測試裡有兩條在盯這句話。

#### 修掉的一個 bug

新版時間線用 `disposition = 'mine_only'` 判斷要不要濾掉對方的內容，
而處置還沒選時它是 `null`——`null = 'mine_only'` 的結果是 `null` 不是 `false`，
接著 `not v_mine_only` 也是 `null`，整個 `where` 變成什麼都不符合。
**一段還沒結束的關係，時間線會整個變空。**

驗證：`pgtest-journal` 41、`pgtest-checkin` 26、`pgtest-clinic` 41、`pgtest-ending` 36、
`smoketest-journal.js` 93。連同既有測試 SQL **575 項**、瀏覽器 **769 項**，全部通過。

**還沒做的**：
- **年度回顧**（規格第 8 步的另一半）要先回答第 7 節第 3 題。**已在第 44 節做完。**
- **回憶的照片**（第 7 節第 2 題）：`photo_path` 欄位留著，但沒有上傳介面。
  私密照片不能放公開 bucket，也不像驗證照那樣審完就刪，需要第三種 bucket 與清理政策，
  而且它的刪除要跟著 `purge_at` 一起走。
- **`purge_at` 的排程**（跟第 36 節檢舉時效通知是同一個缺口）。

### 44. 📖 年度回顧，以及「相互承認彼此是伴侶」

規格第 7 節第 3 題（做年度回顧代表資料要留一年以上，跟隱私權政策的保存期限衝突）
的答案：**年度回顧只給互相承認彼此是伴侶的兩個人。**

於是「保留超過一年」不再是一個對所有人生效的預設，而是一件**兩個人各自明確按下、
而且隨時可以收回**的事。沒有相互承認的關係不提供年度回顧，也就不需要為了年度回顧
多留任何東西——衝突就消失了。原本隱私權政策裡陪伴紀錄根本沒有條文（其他項目寫的是
「保存至你自行刪除」，等於沒有上限），這一輪補上的那一條反而**收緊**了預設。

#### 單方面按下，對方完全不會知道

這是這一節唯一真正難的決定，而且**跟第 42 節（建立陪伴紀錄時會顯示「對方想為這段相遇
留下紀錄」）刻意不一樣**：

> 承認彼此是伴侶不是邀請，是一句告白。
> 把「某某已經認定你是他的伴侶」推到另一個人面前，他接下來按或不按都不再是自由的——
> 按了可能只是不想讓對方難堪，不按則變成一次當面的拒絕。

所以 `companion_partner_state()` 回傳的 `other` **只有在兩邊都按下時才會是 true**，
它不是「對方按了沒有」。畫面上也不會有任何「等待對方」的進度條——那等於變相通知，
另一個人一登入就會知道有人在等他回應。收回一樣安靜。

**這不是等級，也不是成就。** 沒有徽章、沒有恭喜、沒有「配對成功率」，
`get_visible_match_profiles()` 裡也搜不到它——那不是拿來給別人看的東西。
它只做兩件事：讓年度回顧出現，以及讓這本紀錄的保存期限跟著關係走。

#### 年度回顧裡沒有 AI，也沒有數字

就是把那一年你們自己寫下的東西照時間端出來：里程碑、回憶、對話書籤、共同目標。

- 放一個「今年你們記了 12 則回憶」進去，它就會變成一個要衝的數字。
  所以 `companion_annual_review()` **完全不回傳任何 `count` 欄位**，畫面上也沒有。
- 放一段 AI 講評進去，它就會變成一份年度評鑑。所以這一段沒有接 AI。
- 目標只列「完成了」與「先放著」，而且**並列，沒有先後**——先放著不是沒做到，
  是那一年你們決定先不推它。

#### 兩個測試自己的 bug

- **`partner_alone_time_acceptance` 被 `partner_a` 這個 pattern 掃到。**
  我寫的「佈告欄不能出現伴侶狀態」那條斷言沒有用字界，第 23 節的生活場景欄位剛好命中，
  變成一條永遠紅的假警報。改成 `\ypartner_[ab]\y`。
- **樣板字串巢狀四層之後少了一個收尾的 `}`**，整個 `<script>` 掛掉，
  而瀏覽器只說「Missing } in template expression」並指到另一個位置。
  改成先把四段各自組好再塞進版型，不再靠巢狀。

驗證：`tests/pgtest-annual.sql` **42 項**（含「甲按了但乙這邊完全看不出來」
「收回再按回來不重算日期」「回顧裡沒有任何 count／summary 欄位」
「選了全部刪除之後年度回顧也跟著空了」）與 `smoketest-journal.js` 擴充到 **126 項**

「隱私權政策裡也沒有承諾自動刪除」）。
連同既有測試 SQL **617 項**、瀏覽器 **802 項**，全部通過。

`purge_at` 的排程也還是沒有。這兩件事在使用量還小的時候不會出事，
介面上也照實說了目前沒有自動清理在跑。

### 45. 💛 他們的故事：配對成功的伴侶把故事貼出來給其他人看

新增一個**訪客也看得到**的分頁。寫故事的入口在陪伴紀錄裡，只有互相承認彼此是伴侶的
兩個人才有那一格（第 44 節的條件）。

#### 為什麼這一節的守門特別重

這在本質上是**第 41 節那個洞的放大版**。暖陽整套四層漸進式揭露，就是為了讓聯絡方式
要走完三階段、雙方都同意才交換。一個可以自由輸入、而且訪客也看得到的欄位，
等於開了一條把任何文字放到所有人面前的管道——而且是使用者自己開的，不會有人來檢舉。

所以有三道關，缺一不可：

1. **伺服器端擋聯絡方式**（沿用第 41 節的 `looks_like_contact()`）。
   錯誤訊息會說明「這一頁訪客也看得到」，不是只說「不行」。
2. **兩個人都同意才送得出去。**
3. **人工審核通過才公開。** 系統已經擋掉聯絡方式，人看的是別的：
   有沒有寫到第三個人、公司名稱、可以定位到個人的細節。

#### 四條寫死的產品規則

- **改了字，同意就作廢。** 對方同意的是「那一段文字」，不是「你之後想寫的任何東西」。
  這一條沒做的話，第 ② 道關可以被一次編輯整個繞過去——所以 `save_story()` 的
  `on conflict do update` 裡直接把 `agreed_a`／`agreed_b` 歸零。
- **任何一方隨時可以撤下，立刻生效、不需要對方同意、不用寫原因。**
  已經審過的也一樣會掉下來；要再上就重新審一次。
  而且**管理員不能替當事人補上同意**——不然一則被撤下的故事可以被一鍵放回公開頁面。
- **關係結束或收回相互承認，故事自動下架。** 一則屬於已經分開的兩個人的「成功故事」
  留在公開頁面上，對兩邊都是傷害。這一條**不靠排程**，直接做在
  `end_companion_link()` 與 `set_companion_partner()` 裡。
- **具名各自決定，預設都不具名。** 佈告欄上本來就看得到暱稱，但
  「這兩個帳號在一起」是一則新的公開資訊。沒同意具名的顯示成「一位使用者」。

#### 沒有的東西

沒有愛心、沒有瀏覽數、沒有排行榜、沒有精選，排序永遠是最新的在前面。
一旦故事之間可以比較，寫故事就變成一件要表現的事。
公開清單那支 RPC 也不回 `link_id`／`author`／同意狀態——那些流出去等於把
「哪兩個帳號」直接接起來；訪客直接 select 那張表則什麼都拿不到。

管理端退回**一定要寫原因**：沒有原因的退回，使用者只會再送一次一模一樣的東西。

#### 一個測試自己的 bug，一個環境限制

- **`handle_new_match_user()` 會先塞一列空白的 profile**，所以測試 fixture 裡
  `on conflict (id) do update set account_status=...` 沒把 `name` 一起寫進去，
  暱稱就是空字串——結果「同意具名卻沒有名字」看起來像產品壞了。
  （順帶驗證了產品端的 `nullif(name,'')` 會安全地退回「一位使用者」。）
- **`smoketest-journal.js` 加到 154 項之後超過 runall.sh 的 90 秒上限**，
  斷言全綠卻回報 CRASHED。拆成 `smoketest-journal.js`（126）＋
  `smoketest-stories.js`（37）。

驗證：`tests/pgtest-stories.sql` **42 項**（含「改了字之後兩邊的同意都作廢」
「任一方撤回，公開頁面立刻就沒有了」「沒有雙方同意時管理員不能公開它」
「關係一結束故事立刻下架」「訪客直接 select 這張表拿不到東西」）
與 `smoketest-stories.js` **37 項**。
連同既有測試 SQL **659 項**、瀏覽器 **839 項**，全部通過。

### 46. 📷 對話相簿（7 天過期）與 📬 待審通知

#### 相簿：規格第 7 節第 2 題的答案

原本卡住的是「陪伴紀錄的照片要放哪個 bucket、清理政策怎麼訂、刪除要不要跟著
`purge_at` 走」。答案把整道題**解掉**了，不是繞過去：

> 照片不進陪伴紀錄，也不長期保存。它們待在對話旁邊的相簿裡，**7 天之後就看不到了**。
> 想留下來的人自己按 ⬇️ 下載。

沒有長期私密儲存，就沒有那個 bucket 的清理政策問題，也不必跟 6.1 綁在一起。

**過期怎麼真的發生**，分兩層講，因為排程還是沒有：

- **看得到／看不到**：`list_chat_photos()` 以 `expires_at` 過濾，時間一到 App 裡就拿不到。
  更重要的是 **Storage 的讀取政策裡也有 `expires_at` 這個條件**——
  少了它，過期的只是在畫面上不見了，知道路徑的人還是拿得到，那就等於沒有過期。
  這一條有測試直接去讀那條 policy。
- **檔案本身**：前端在列相簿時會順手把**自己上傳、已經過期**的那幾個從 Storage 刪掉
  （只刪自己的——別人的檔案自己沒有權限刪，也不該有）。這涵蓋還有人在打開的對話；
  沒人再打開的要靠排程。所以介面上只承諾「看不到」，**不承諾「已經從伺服器上消失」**。

**一句必須在畫面上的話：會過期不等於安全。** 對方在這 7 天內可以下載、可以截圖，
暖陽擋不住，任何軟體都擋不住。一個看起來會「自動消失」的相簿，如果讓人以為傳私密照片
是安全的，那比不做這個功能更糟。所以文案裡完全沒有「放心傳」「閱後即焚」這種說法，
而且有測試盯著。收回也一樣：按鈕會先講明「已經下載或截圖的收不回來」。

其他：路徑一定要在該段對話的資料夾底下（不然 Storage 政策形同虛設）、
說明欄一樣擋聯絡方式、一段對話同時最多 30 張未過期的、申請被退回之後不能再傳。

#### 待審通知：做成 outbox，不在 trigger 裡發信

問題是人工審核沒有通知，站方要自己進後台才知道有東西待審。

在 trigger 裡直接打 HTTP 出去有三個問題：外部服務掛掉會讓使用者那一次送出檢舉／回饋
**整個失敗**；沒有重試；而且發生了什麼完全看不到。所以資料庫只負責記一筆
`owner_notifications`（第 35 節），真正寄信的是 Edge Function。

**送不出檢舉比收不到通知嚴重得多**，所以 `queue_owner_notification()` 把例外整個吞掉。
有一條測試專門裝一個會炸的 trigger 在 outbox 上，確認檢舉照樣送得出去。

管理後台頂端有一條**通知狀態**。它的用途是**揭穿自己**：如果通知從來沒接上，
`pending` 會一直往上長，而站方會在那裡看到「看起來還沒設定」。
沒有這一塊的話，「有做通知」會變成一個沒有人驗證過的假設。

#### 要怎麼設定（這一段是給站長照著做的）

程式都寫好了，但**我沒有辦法替你部署，也不能替你保管 API 金鑰**，所以要你自己跑一次。

> **不需要安裝 Supabase CLI。** `supabase functions deploy` 是 CLI 指令，
> 沒裝當然找不到。底下走的是**全程在後台點**的路線。
> （習慣用 CLI 的話，最後面有 CLI 版。）

**1. 申請寄信服務**
到 <https://resend.com> 註冊（免費方案每天 100 封、每月 3000 封，遠超過需要），
建立一組 API Key，長得像 `re_xxxxxxxx`。

**2. 產一組通知密鑰**
隨便一串夠長的亂數就好，等一下第 4、5 步都要用。例如在瀏覽器 console 執行：
```js
crypto.randomUUID() + crypto.randomUUID()
```
記下來，這組**不要 commit 進 repo**。

**3. 在後台建函式**
Supabase Dashboard → 左邊 **Edge Functions** → **Deploy a new function**
→ 選 **Via Editor**（或「Create a new function」之類的按鈕，不同版本字樣略有差異）
→ 名稱填 `notify-owner`
→ 把 `supabase/functions/notify-owner/index.ts` **整份**貼進編輯器
→ **Deploy**。

> ⚠️ **建立時就要把名稱填對，事後改不了。**
> 後台建函式如果沒填名稱，Supabase 會自動給一個隨機代號
> （`rapid-worker`、`swift-badger` 這種）。而那個代號**就是網址**，
> 之後在設定頁改「Name」只會改顯示名稱——那一頁自己也寫著
> 「Your slug and endpoint URL will remain the same」。
>
> 症狀是：後台明明看得到一支叫 notify-owner 的函式，
> 打 `/functions/v1/notify-owner` 卻一直回 `NOT_FOUND`。
> **以函式頁面最上方顯示的那個網址為準**，那才是真的。
> 名稱錯了就砍掉重建，比繼續用一個叫 rapid-worker 的通知函式好。
>
> 貼完程式碼後順手核對行數（目前 184 行）與最後一行（`});`）。
> 行數對不上代表貼到舊版或沒貼完，而部署一樣會成功，
> 只是跑的是舊的程式碼——那種錯最難查。

**4. 把這支函式的「Verify JWT」關掉**　← ⚠️ 這一步不做，後面一定會 401
進到 `notify-owner` 的 **Settings / Details**，找到 **Verify JWT**（或
「Enforce JWT Verification」）並**關閉**。

為什麼：平台預設會先驗使用者 JWT，而排程與 Webhook 帶的不是使用者 JWT，
會在函式自己的檢查跑到之前就被擋掉。關掉之後，把關的是函式裡的
`x-notify-secret` 檢查——**所以第 5 步的 `NOTIFY_SECRET` 一定要設，那是唯一的一道門。**

**5. 設定 secrets**
Edge Functions → **Secrets**（或 Project Settings → Edge Functions → Secrets），加四筆：

| 名稱 | 值 |
|---|---|
| `RESEND_API_KEY` | 第 1 步拿到的 `re_xxxxxxxx` |
| `NOTIFY_TO` | `warmsun.shelter@gmail.com` |
| `NOTIFY_FROM` | `暖陽動物之家 <onboarding@resend.dev>` |
| `NOTIFY_SECRET` | 第 2 步那組亂數 |

`onboarding@resend.dev` 是 Resend 提供的測試寄件網域，**不必先驗證自己的網域**就能寄；
之後有自己的網域再換掉。
`SUPABASE_URL` 與 `SUPABASE_SERVICE_ROLE_KEY` 是平台自動注入的，**不用自己設**。

**6. 先手動測一次**（在排程之前，這樣才知道是哪一步壞的）

專案代號在 `js/config.js` 的 `SUPABASE_URL` 裡就看得到。

**最省事的測法：直接在瀏覽器開這個網址**（把密鑰放在網址上）：
```
https://<專案代號>.supabase.co/functions/v1/notify-owner?secret=<第 2 步那組亂數>
```
會看到 JSON 回應。這樣測不會觸發 CORS 預檢，所以**看到的錯誤就是真正的錯誤**。

> 為什麼不用 `x-notify-secret` 標頭測：自訂標頭會讓瀏覽器先送一個 OPTIONS 預檢，
> 而預檢依規格不帶任何自訂標頭。只要 Verify JWT 還開著，預檢就會被閘道擋掉，
> 而瀏覽器只會說「CORS policy: preflight ... does not have HTTP ok status」——
> 那個訊息看起來像 CORS 壞了，實際上是授權被擋。查起來會繞很久。
>
> ⚠️ 網址會進瀏覽器紀錄與伺服器 log，所以**排程請用標頭那一種**，
> 網址參數只拿來做一次性的測試。

有終端機的話 curl 也可以（Windows 用 PowerShell 的話要把換行的 `\` 拿掉寫成一行）：
```bash
curl -i -X POST -H "x-notify-secret: <第 2 步那組亂數>" \
  https://<專案代號>.supabase.co/functions/v1/notify-owner
```

**回應怎麼讀：**

| 回應 | 意思 |
|---|---|
| `{"sent":N}` | 成功，信應該進信箱了 |
| `{"sent":0,"note":"沒有待寄的通知…"}` | 也是成功，只是現在沒東西要寄。先去網站送一則意見回饋再測一次 |
| 完全沒有 JSON（瀏覽器報 CORS、或 `Missing authorization header`） | 第 4 步的 Verify JWT 還開著——函式根本沒被叫到，被閘道擋掉了 |
| `401` **而且看得到這段 JSON**（`{"error":"unauthorized",...}`） | 函式是活的，JWT 沒問題，是 `NOTIFY_SECRET` 沒對上。回應裡的 `診斷` 欄位會告訴你：有沒有收到你送的密鑰、長度多少、伺服器那邊有沒有設——照著比對就找得到是哪一邊漏了或打錯了（常見是複製時多帶了空白或換行，函式會自動去頭尾空白但不會處理中間） |
| `500` 提到 `Could not find the function` | 最新的 `supabase-schema.sql` 還沒貼進 SQL Editor |
| `500` 提到 `RESEND_API_KEY` | 第 5 步漏了 |
| `502` | Resend 退件，`detail` 裡有原因（多半是 `NOTIFY_FROM` 寫錯） |

**7. 讓它定時跑**
Dashboard → **Integrations → Cron** → 新增排程，每 15 分鐘呼叫一次
`https://<專案代號>.supabase.co/functions/v1/notify-owner`，
HTTP headers 加上 `x-notify-secret: <第 2 步那組亂數>`。

一次寄一封摘要，不會每件事一封信。
（也可以改用 **Database Webhooks**，設成「`owner_notifications` 有 INSERT 就呼叫」，
那是即時的。這支函式每次都會把待寄的全部合成一封並標記，所以**不會重複寄**。）

**8. 驗收**：管理後台頂端那條「待審通知」的 pending 會回到 0，
而且不再顯示「看起來還沒設定」。

**沒有做這幾步也完全不影響網站**——所有功能照常，只是沒有人會收到 email，
而後台會一直顯示「看起來還沒設定」。

### 47. 修掉一個「第一次貼沒事、第二次貼才炸」的 bug

站長把最新的 `supabase-schema.sql` 貼進 SQL Editor 時撞到：

```
ERROR: 23514: check constraint "chat_safety_signals_class_check"
of relation "chat_safety_signals" is violated by some row
```

**原因是同一個 check 的允許值清單被定義在兩個地方**：第 24 節一份、
第 30 節為了加 `reported_harm` 又寫了一份。第 24 節那份比較窄，於是——

- **第一次貼** → 完全正常（第 30 節那份最後生效）
- **第二次貼** → 第 24 節那份把清單改窄，而第 30 節上一輪插進去的
  `reported_harm` 資料違反了它 → 23514

而 README 從第一天就寫著「改完重新貼一次整份 schema 就好」，
所以這等於把那句話直接弄假了。

**修法**：class 清單只留第 24 節那一份（補上 `reported_harm`），
第 30 節只保留 insert。用 `grep` 掃過整份檔案，
`chat_safety_signals_class_check` 是**唯一**被定義兩次的約束。

#### 為什麼既有的升級測試沒抓到

`pgtest-upgrade.sql` 的流程是「把資料庫降版 → 重貼」，而**降版那一步剛好會
刪掉新版才有的那幾列**（我上一輪還特地把 `reported_harm` 加進刪除清單）。
於是那個流程永遠測不到「已經是新版的資料庫，再貼一次」——
而那正是站長每次實際會做的事。

補了兩道防線：

- **`pgtest-upgrade.sql` 第四段**：直接再 `\i supabase-schema.sql` 一次。
  `ON_ERROR_STOP` 開著，任何 23514 都會停在那裡。
  （已用「把修正拿掉」驗證過它真的會紅。）
- **`tools/check-schema.mjs`**：靜態掃描，同一個 constraint 名稱出現兩次就
  直接失敗，而且印出兩處的行號。這道在跑資料庫之前就會擋下來。
  目前 28 個 constraint 全部只有一個定義處。

#### 順帶一提：另一個錯誤訊息

同時看到的 `syntax error at or near "<!"` `LINE 1: <!DOCTYPE html>`
是把**網頁**貼進 SQL Editor 了——從 GitHub 的檔案瀏覽頁複製會連 HTML 一起帶走。
要用 Raw：

```
https://raw.githubusercontent.com/arink393-ai/warmsun-adoption-match/main/supabase-schema.sql
```

### 48. 送出申請前先提醒「不可妥協條件衝突」，不擋

使用者對整個網站給了一輪完整的產品評估，結論大致是：**篩「不適合的人」已經做得不錯，
但還沒有篩出「有能力經營長期關係的人」**。裡面第一個、也是最容易落地的一條建議是：
與其讓兩邊都填了不可妥協條件、卻要等對方審查申請時才第一次看到衝突，
不如**在使用者按下「提出認識邀請」的當下**就先講。

兩個設計決定不是我自己猜的，是先用 `AskUserQuestion` 問過使用者才動工：

- **提醒，但不擋**。衝突再多，送出鍵仍然按得下去——這裡假設「兩邊都想試試看」
  本身也是一種有效的資訊，系統不該替兩個成年人做這個決定。
- **只講數字，不講是哪一項**。跳出來的視窗只會說「你們有 2 項不可妥協條件互相衝突」，
  不會列出是收入、婚姻觀還是其他哪一項。這是刻意的：一旦講出欄位名稱，
  接下來很容易變成「所以你就是嫌我收入低？」這種對話，而那正是這個提醒最不該引發的結果。

**沒有另外做一套判定邏輯。** 🔴（不可妥協）本來就已經定義在 `run_screening()`
裡——兩邊都把同一個題組標成 non-negotiable，而且答案衝突，才算🔴。新函式
`check_hard_filter(p_target)`（schema 第 36 節）直接借用同一套規則與同一份
`screening_results` 快取，只回傳 `{"conflicts": N}` 一個數字。這樣「送出前顯示
2 項衝突」跟對方稍後看到的初診報告一定對得起來，不會有兩套算法各說各話的風險。

前端 `openApply()` 在打開申請表之前先呼叫這支 RPC；有衝突才跳原生 `confirm()`，
取消就整個放行流程直接中止、不送出任何東西。呼叫本身失敗（離線、還沒登入、
還沒建好 profile 等）一律當作沒有衝突、直接放行——这一步是額外的體貼，
不能反過來變成申請流程的新故障點。

#### 寫測試時抓到的一個純粹的測試方法論陷阱

第一版 SQL 測試把「送出前的預檢」跟「稍後真正送出申請後看到的報告」寫在同一個
`do $$ ... $$` 區塊裡，結果案例三間歇性地判斷「快取還新鮮」為假,實際上兩次呼叫
之間資料明明沒變。追下去發現：`screening_results.ran_at` 用的是 `clock_timestamp()`
（同一個交易內每次呼叫都會前進），但 `match_profiles.updated_at` 是由
`BEFORE UPDATE` trigger 用 `now()` 寫入的（同一個交易內永遠凍結在交易開始那一刻）。
把預檢跟送出寫在同一個交易裡，等於製造出一個真實情境不會發生的時間錯位——
真正的兩次請求本來就是兩個獨立的交易。修法是把測試拆成兩個獨立的
`do $$ $$` 區塊，模擬兩次分開的 HTTP 請求。這是測試方法論本身的陷阱，
不是產品的 bug，程式一行都沒改。

驗證：`tests/pgtest-hardfilter.sql` **15 項**（0 衝突直接放行、2 衝突且不洩漏欄位名稱、
跟 `get_screening_for` 給出的數字保持一致、警告不擋送出、自己／不存在的人／已封鎖／
未登入等邊界情況）與 `smoketest-hardfilter.js` **21 項**（有衝突才跳提醒、訊息裡完全
不出現任何欄位名稱、取消不送出、RPC 失敗時照樣放行、確認後送出的對象正確）。
連同既有測試共 SQL **716 項**、瀏覽器 **876 項**，全部通過。

**還沒做**：使用者這輪建議裡另外兩塊——「❤️ 關係能力評估」（6 題情境式能力問卷，
只給審查者看原始回答文字，不做成分數或燈號）與「私人自我回報的感受紀錄／約會後的
Reality Check 私人日記」——是下一輪要做的事，設計方向已經在跟使用者確認過，
還沒動工。

### 49. ❤️ 關係能力評估（Relationship Readiness）

使用者那輪產品評估的第二條建議，也是評估裡份量最重的一條：暖陽已經很會篩
「不適合的人」（💞 相容度：條件對不對得起來），但還沒有篩出「有能力經營
長期關係的人」。第 48 節的 Hard Filter 提醒解決的是前者的最後一塊拼圖；
這一節補的是後者，是一條跟 💞 相容度互相獨立的新軸線，不是取代它。

**6 題情境式問題，問的是「上一次實際上怎麼做」。** 衝突後的修復、界線尊重、
情緒責任、當責、互惠、自主與空間——每一題都要求寫一次真實發生過的例子，
不是「你覺得自己是怎樣的人」。自我認知跟實際行為常常對不起來，問「上一次
實際上怎麼做」比較不容易變成自我行銷。全部選填，可以整步跳過。

跟這條建議一起送來的，還有使用者自己提出的兩個選項，都先用 `AskUserQuestion`
問過使用者才動工，而不是我自己猜：

- **審查申請的人看到的是什麼？** 曾經考慮過讓系統把 6 段回答算成
  🟢🟡🔴 分類。使用者自己也點出這個做法的問題——自我回報的分數很容易變成
  自我行銷——最後選了**只給看原始回答文字**。系統不對一段自由文字下判斷，
  要不要打折扣、要追問什麼，留給真人自己決定。
- **要不要做題庫版本管理？** 沒有。跟第 29 節的 `checkin_questions()`
  同一個模式：題目是 SQL 函式 `readiness_questions()` 回傳的 jsonb，
  前端用 RPC 現讀，不在 `index.html` 裡再抄一份題目文字。

**沒有輸出任何分數。** 跟第 22 節刪掉 `vet_scores`、第 29 節 checkin 不做
Relationship Health Score 同一個理由：沒有校準基礎的數字或燈號一旦出現，
就會被當成結論。畫面上顯示原始回答文字的地方（第 7 步的說明與病歷卡上），
一定帶著這句話：「這不是人格診斷，也不代表對方一定會如此行動。結果只用來
指出值得進一步確認的地方。」

**揭露層級刻意跟宗教／感情史同一層，比學歷晚一層。** 6 段敘事文字的識別度
與敏感度都比單選欄位高，所以 `get_visible_match_profiles()` 把 `readiness`
放在第 2 層（進入第二階段才看得到），不是跟身高學歷同一層的第 1 層。

實作上刻意選了「白名單獨立寫兩份、互相不呼叫」而不是「兩處互相呼叫同一份」：
存檔驗證的 `guard_profile_custom_text()` trigger（第 26.3 節）在資料庫剛建立、
`readiness_questions()`（第 37 節）都還沒定義的當下就要能跑，兩者物理位置
天生就不同順序。兩份清單只要有一個字不一樣，`tests/pgtest-readiness.sql`
會直接紅（逐一拿 `readiness_questions()` 的 6 個 key 去試存檔）。

前端也有一個對應的小心思：題目文字是用 RPC 在頁面載入時就先讀的
（`renderReadinessFields()`），不是等使用者切到第 7 步才發請求；儲存登記時
如果這支 RPC 還沒讀到或讀取失敗，`collectExtraFields()` 會**完全不放
`readiness` 這個 key 進存檔內容**，不會送一個空物件——送空物件的下場是
使用者只是手腳快了一點先按了儲存，先前填好的六題就被一次洗空，而且他
不會知道為什麼。這一條用負測試驗證過：把判斷條件改成永遠成立，
`smoketest-readiness.js` 立刻抓到「六題被洗空」。

驗證：`tests/pgtest-readiness.sql` **16 項**（存檔白名單、聯絡方式與長度上限、
題庫與白名單同步、三層揭露、沒有分數）與 `smoketest-readiness.js`
（未入庫，慣例同其餘瀏覽器測試放在 scratchpad）**24 項**（第 7 步的題目與
免責聲明、既有回答回填、存檔內容、RPC 失敗不洗空既有回答、病歷卡顯示）。
連同既有測試共 SQL **732 項**、瀏覽器 **900 項**，全部通過。

**還沒做**：使用者這輪建議裡剩下兩塊——私人自我回報的「感受紀錄」（對話後
的 😊被尊重／😣有壓力等 chips，只給本人自己看趨勢，不用於標記對方）與
約會後的 Reality Check 私人日記——是下一輪要做的事，設計方向已經在跟
使用者確認過（都是完全私人、不對外顯示、不做為篩選條件），還沒動工。

## 已知限制（原型階段）

### 只能在 Supabase 控制台做，程式改不到

- **外洩密碼防護**要在 Supabase 控制台另行啟用：
  **Authentication → Policies（或 Sign In / Providers → Password）→ 開啟
  「Prevent use of leaked passwords」**。它會拿密碼去比對 HaveIBeenPwned 的外洩清單，
  純粹是專案設定，前端與 schema 都碰不到。同一頁順便把最小密碼長度調到 8 以上——
  網站的表單目前擋的是 6，那是配合 Supabase 的預設值。

### 需要真人帳號才能驗收

- 完整的聊天、管理員操作與刪帳流程，需要至少**兩個一般測試帳號加一個管理員帳號**
  實際登入跑一遍。自動化測試攔掉了 Supabase，驗的是畫面邏輯，不是真的 Auth 與 RLS。
  第 4c 步的驗收清單就是給這件事用的。

### 產品上的取捨，不是還沒做

- 使用者安全仍依賴**人工審核與檢舉處理**；系統不會自動判定詐騙、騷擾或照片相似度。
  使用者端可以自己封鎖（見第 24 節安全中心），但站方端的判斷是人工的。
  這是刻意的——自動判定一個人是不是詐騙，錯誤的代價由被誤判的人承擔。
