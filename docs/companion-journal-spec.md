## 1. 定位：這不是「認養後追蹤」

寫在最前面，因為它會決定後面每一個 UI 的語氣：

> 動物之家不監控你們的關係，也不要求回報。
> 暖陽只是把診療室留著——需要整理回憶、確認關係狀態、處理衝突，
> 或想記下一件值得記住的事情時，可以再回來。

由此推出三條產品規則，實作時不能違反：

- **不用建立陪伴紀錄也能解鎖聯絡方式。** 配對功能在第三階段就完成了，
  陪伴紀錄是額外價值，不是解鎖條件。放成條件的話，它就從「值得回來的理由」
  變成「不做就拿不到東西的關卡」。
- **不做每 N 天強迫填的問卷。** 健康檢查每月最多一次，而且完全選填，也不主動狂推。
- **使用者離開不算失敗。** 兩個人交換聯絡方式後再也沒登入，可能代表暖陽已經完成它的工作。
  這一條要寫進程式碼的註解裡，因為它會直接反對「加一個每日簽到」這類提案。

## 2. 資料模型

六張新表，跟配對資料分開。**分開的理由不是整潔，是權限**：
配對資料的 RLS 是「申請雙方可讀」，陪伴紀錄的 RLS 是「這段關係的兩個人可讀」，
兩者的主體不同（申請會結案，關係不會）。

```sql
-- 哪兩個人建立了陪伴關係　※ 已實作（schema 第 27 節），實際欄位如下
companion_links(
  id uuid pk, user_a uuid, user_b uuid,   -- check (user_a < user_b)，寫入前先排序
  application_id uuid,          -- 從哪一份申請走過來的（可為 null，之後可能有別的入口）
  started_at timestamptz,       -- 只在 pending → active 那一次寫入，暫停再回來不重算
  status text check (status in ('pending','active','paused','ended')),
  agreed_a boolean, agreed_b boolean,     -- 兩個都 true 才會變成 active（見第 7 節第 1 題）
  ended_at timestamptz, purge_at timestamptz,
  disposition_a text, disposition_b text, -- 見 6.1
  unique (user_a, user_b)
)

-- 🔖 記住這句：聊天與陪伴紀錄之間的橋　※ 已實作
message_bookmarks(
  id uuid pk, application_id uuid, message_id bigint, user_id uuid,
  kind text check (kind in ('love','milestone','promise','memory')),
  note text,                    -- 只有自己看得到，改成 both 也不會分享出去
  visibility text check (visibility in ('private','both')) default 'private',
  created_at timestamptz,
  unique (message_id, user_id)  -- 一則訊息一個人一個書籤
)

companion_memories(
  id, link_id, at date, type text, title text, body text,
  photo_path text,              -- Storage 的私密 bucket，不是公開 bucket
  created_by uuid,
  visibility text check (visibility in ('both','private'))
)

companion_milestones(
  id, link_id, milestone_type text, at date, note text, created_by uuid
)

companion_goals(
  id, link_id, title text, category text,
  status text check (status in ('idle','doing','done','paused')),
  created_by uuid, completed_at timestamptz
)

relationship_checkins(
  id, link_id, user_id, answers jsonb,
  share_with_partner boolean not null default false,   -- 預設 false，見第 4 節
  created_at timestamptz
)

clinic_sessions(
  id, link_id, user_id, topic text, input text,
  ai_summary jsonb, followup jsonb, saved boolean, created_at timestamptz
)
```

**`companion_goals.status` 一定要有 `paused`（暫時放下）。** 只給「未開始／進行中／完成」
會讓「這件事我們現在不想推」變成沒有地方可以表達，只能留在「未開始」裡看起來像拖延。
關係不是專案管理。

## 3. AI 讀取權限：這是最容易做錯的地方

**私人聊天預設不是 AI 的輸入，也不是主治醫師的自動讀取範圍。**

```sql
clinic_context_permissions(
  link_id, user_id,
  allow_profile boolean,        -- 我的病歷卡
  allow_dealbreakers boolean,   -- 我的不可妥協項目
  allow_stage2 boolean,         -- 第二階段回答
  allow_checkins boolean,       -- 過去的健康檢查
  allow_sessions boolean,       -- 過去的診療紀錄
  allow_goals boolean,          -- 共同目標
  allow_chat_range int,         -- 允許讀取最近幾天的對話，0 = 不允許
  updated_at timestamptz
)
```

> **實作時偏離了這裡：`allow_chat_range` 沒有做。**
> 一個叫 `allow_*` 的欄位存在資料庫裡，遲早會有人把它當成常設開關讀，
> 而那正好違反下面第 (2) 條自己寫的「那個授權是一次性的，不是永久開關」。
> 改成 `last_chat_days`：只記上一次勾了幾天、純粹拿來預填畫面，
> `build_clinic_context()` 從頭到尾不看它，天數一律當次傳入。
> 另外多了一個 `allow_joint`（共同關係分析的同意），對應第 (3) 條。
>
> 由第 (3) 條再推出一條規格沒寫、但不補上就會破功的規則：
> **對話只能在 joint 模式、而且兩個人都同意時才進得了 AI 的輸入。**
> 對話裡有對方說的話；solo 模式說好了「只讀使用者自己給的片段」，
> 就不能從後門把整段對話撈進去。

三條硬規定：

1. **預設全部 false。** 進診療室不會自動把所有歷史翻出來。
   每一次要讀什麼，都是使用者當下勾的。
2. **對話只能整段授權、不能整本授權。** 「分析我們最近一個月聊天」必須明確勾
   「我同意主治醫師讀取最近 30 天對話」，而且那個授權是一次性的，不是永久開關。
3. **共同關係分析要雙方同意；只幫一個人整理感受則不需要。**
   界線是：**輸出裡有沒有對另一個人的判斷**。
   「幫我整理我的感受」只讀使用者自己給的片段，**不替另一方建立人格診斷**。
   這一條跟第 34 節「AI 不輸出百分比、不替對方貼標籤」是同一個原則的延伸。

## 4. 健康檢查：兩個人的答案不會自動互通

A 填「最近覺得孤單」，系統**不會**通知 B「你的伴侶說跟你交往很孤單」。
那只會直接製造一場架，而且會讓人下次不敢誠實填。

所以 `share_with_partner` 預設 `false`。只有**兩邊都選擇分享**時，才產生共同觀察，
而且共同觀察的措辭是「你們最近都覺得工作比較忙」這種並列描述，不是轉述指控。

**不輸出分數。** 不做 `Relationship Health Score: 64%`——理由跟第 34 節把
`vet_scores` 整欄刪掉一樣：沒有校準基礎的數字會被當成結論。
改成「本次回診摘要」，指出狀態與一個可以談的方向。

## 5. 診療室：協調者，不是仲裁者

寫死的產品規則：**主治醫師不判誰有理。** 不寫「A 比較合理」「B 應該道歉」。
輸出固定四段：

| 段落 | 內容 |
|---|---|
| 事實 | 發生了什麼 |
| 感受 | 各自在意什麼 |
| 需求 | 可能需要什麼 |
| 下一個問題 | 現在最值得談的是什麼 |

**唯一的例外是安全。** 輸入若涉及人身安全（「他打我，但我不知道是不是我先惹他生氣」），
必須離開關係協調模式，切換成安全模式：

> 這件事情涉及人身安全，不適合當成一般伴侶衝突協調。
> 暖陽會優先協助你整理安全選項，而不是要求你和對方折衷。

**不能回答「你們可以試著理解彼此的需求」。** 在有人身安全疑慮的情境裡，
「各退一步」這種建議會把責任推回受害的一方。
這一段要跟現有的安全中心連動，而且要有測試盯著——跟第 24 節對話室的 🔴 同一個等級的底線。

> **實作時發現第 24 節的偵測抓不到這一節舉的例子。**
> 對話室那套看的是「有人在對另一個人要求或威脅」，而
> 「他打我，但我不知道是不是我先惹他生氣」沒有威脅任何人——
> 它是受害者在轉述發生在自己身上的事。
> 所以另外開了一類 `reported_harm`（schema 第 30.2 節），只給診療室與意見回饋用；
> 在對話室裡命中的會是受害者自己那則訊息，替受害者的訊息標紅燈是最糟的結果。
> 跟第 25 節既有的 `reported` 分開，是為了不要把「他逼我太緊」這種關係壓力
> 也推進安全模式——那會讓人不敢談日常的拉扯。
>
> 另外，命中安全模式時**根本不呼叫 AI**。把這種輸入交給一個關係協調的 prompt，
> 最好的結果也只是勸和。

## 6. 已經決定的兩題

### 6.1 關係結束之後：本人選處置方式，30 天後系統自動刪除

**決定：由使用者自己選，而且有一個明確的期限。**

關係轉成 `ended` 的時候，兩邊各自收到一次選擇（各自選各自的，不需要對方同意）：

| 選項 | 意思 |
|---|---|
| 🗑️ 全部刪除 | 我在這段關係裡寫的東西全部刪掉 |
| 📦 封存唯讀 | 保留，但誰都不能再新增或修改 |
| ✍️ 只留我自己寫的 | 我寫的留著，對方寫的從我這邊移除 |

```sql
alter table companion_links
  add column ended_at timestamptz,
  add column purge_at timestamptz,            -- ended_at + 30 天
  add column disposition_a text,              -- 'delete' | 'archive' | 'mine_only'
  add column disposition_b text;
```

**30 天的意義是「選擇的期限」，不是「保留的期限」**，這兩個很容易寫反：

- 期限內選了 → **立刻**照選的做，不用等 30 天。
- 期限內沒選 → 到期時**自動刪除**。沒有回應不能被當成「同意永久保留」——
  分手之後最可能發生的事就是再也不登入，而那不是同意。

所以 `purge_at` 到期時的動作是**刪除**，不是封存。預設值要站在「少留一點」那一邊。

**一方選封存、另一方選刪除時**：各自的內容各自處置。
選刪除的那一方寫的東西會從封存本裡消失，封存本會留下「這裡原本有 N 則已被作者刪除」
的痕跡，而不是安靜地少幾則——不然另一方會以為自己記錯了。

> ⚠️ **這需要排程。** `purge_at` 到期自動刪除要有東西去跑它（Supabase 的 pg_cron
> 或 Scheduled Function），跟第 36 節檢舉時效通知是同一個缺口。
> 沒有排程的話，這條政策就只是寫在文件上而已。
> 最小可行做法：一支每天跑一次的函式，`delete ... where purge_at < now() and disposition is null`。
> **在排程接上之前，不應該對使用者承諾「30 天後會自動刪除」**——
> 承諾了卻沒有東西在執行，比不承諾更糟。

### 6.2 回憶膠囊：關係非 active 時不自動開啟

**決定：不自動開，改成本人決定要不要看。**

半年後自動跳出來的那封信，如果那時候兩個人已經分開了，它會變成傷害。
所以開啟條件多一個判斷：

- `companion_links.status = 'active'` → 到期自動顯示，照原設計。
- 其他狀態 → **不主動顯示**，改成在陪伴紀錄裡靜靜列一行
  「你有一封 2026/09/17 寫下的信」，點了才打開，而且點之前先問一次。

膠囊本身不因為關係結束就刪除——它是本人寫給自己的，處置方式跟著 6.1 的選擇走。

## 7. 還需要你決定的分岔點

1. ~~**單方面可以建立陪伴紀錄嗎？**~~ **已決定（實作第 1、2 步時）**：拆成兩件事，
   兩個選項各取一半，順便避開了 (b) 的「兩本紀錄後來要合併」。

   - **共同的那本**（`companion_links`）走 (a)：兩個人各自按下才成立，
     跟 Consent Mode 同一個模式。一本關於兩個人的紀錄不該由一個人替兩個人決定，
     而且未經邀請的「某某想跟你建立陪伴紀錄」本身就是一種壓力。
   - **書籤走 (b) 的精神**：`message_bookmarks` 預設 `private`，
     留一句話不需要對方批准，也不會通知對方；想分享再自己改成 `both`，
     而且共同的是那個標記，不是備註裡那段心情。

   於是「回憶是自己的」與「共同的東西要雙方同意」同時成立，
   而且不必合併兩本紀錄——書籤從一開始就掛在同一段對話上，只是可見範圍不同。

2. **照片存哪裡。** 陪伴紀錄的照片是私密內容，不能放公開 bucket。
   但也不像驗證照那樣審完就刪。需要第三種 bucket 與對應的清理政策，
   而且它的刪除要跟著 6.1 的 `purge_at` 一起走。

3. ~~**年度回顧的資料保留期。**~~ **已決定**：
   **年度回顧只給互相承認彼此是伴侶的兩個人。**
   條件是兩個人都願意承認對方是自己的伴侶——也就是已經走到會把對方稱為伴侶的階段。

   這樣一來，「保留超過一年」不再是一個對所有人生效的預設，
   而是一件兩個人各自明確按下、而且隨時可以收回的事。
   沒有相互承認的關係不提供年度回顧，也就不需要為了年度回顧多留任何東西，
   跟隱私權政策的衝突就消失了（隱私權政策第三節已經照這個寫法更新）。

   **實作時多決定了一件規格沒問的事：單方面按下不會讓對方看到，
   連「對方按了沒有」都不會。** 這跟第 1 題（建立陪伴紀錄時會顯示
   「對方想為這段相遇留下紀錄」）刻意不一樣，理由是：
   承認彼此是伴侶不是邀請，是一句告白。把「某某已經認定你是他的伴侶」
   推到另一個人面前，他接下來按或不按都不再是自由的——
   按了可能只是不想讓對方難堪，不按則變成一次當面的拒絕。

   年度回顧本身**沒有 AI，也沒有任何數字**：就是把那一年你們自己寫下的東西
   照時間端出來。放一個「今年你們記了 12 則回憶」進去，它會變成一個要衝的數字；
   放一段 AI 講評進去，它會變成一份年度評鑑。兩個都不要。
